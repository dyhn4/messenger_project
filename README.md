# TangoTalk

Flutter(PC + Android) 클라이언트와 Node.js(Express + Socket.io + PostgreSQL) 서버로 이루어진
개인/소규모 그룹용 실시간 메신저입니다. 텍스트/이미지/파일/이모티콘 채팅, 토픽·그룹·1:1 채팅방,
댓글(스레드), 종단간 암호화(E2EE) 비밀 대화, FCM 푸시 알림, 자체 배포/업데이트 체계를 갖추고 있습니다.

> 이 문서는 실제 소스 코드(스키마, 라우터, 클라이언트 화면, 빌드/배포 스크립트)를 기준으로
> 작성되었습니다. 코드와 다른 내용을 발견하면 이 문서보다 코드를 신뢰하세요.

## 소개

Firebase는 Windows 데스크톱을 공식 지원하지 않아서(Android/iOS/macOS/Web만 지원), 인증·채팅·파일
전송을 전부 자체 Node.js 서버 하나로 통합했습니다. FCM(푸시 알림)만 Android 클라이언트에서
선택적으로 사용합니다.

| | 역할 |
|---|---|
| `client/` | Flutter 앱 — Windows 데스크톱 + Android. PC는 넓은 화면에서 사이드바+채팅 분할 레이아웃, 좁은 화면(모바일)은 목록→채팅 전환 레이아웃(`client/lib/screens/home_screen.dart`의 `wideBreakpoint = 700`) |
| `server/` | Node.js(Express + Socket.io) 백엔드 — 인증(JWT), 실시간 메시지/이벤트, 파일 업로드, PostgreSQL 저장, FCM 발송 |

## 주요 기능

아래는 실제 라우터(`server/src/*.js`)와 클라이언트 화면(`client/lib/screens`, `client/lib/widgets`)
코드를 기준으로 확인된, **현재 동작하는** 기능만 정리한 목록입니다.

**계정**
- 회원가입/로그인, JWT AccessToken(1시간)+RefreshToken(30일) 발급/재발급
- 회원가입 시 보안 질문(프리셋 5종 중 선택 또는 직접 작성)+답변 **필수** 등록
- 아이디 찾기(이메일로 조회) → 그 자리에서 바로 비밀번호 찾기로 이어가기
- 비밀번호 찾기: 아이디+이메일 확인 → 보안 질문 답변 확인(계정에 질문이 없으면 생략) → 새 비밀번호 설정, 단계별 플로팅 다이얼로그
- 프로필: 이름/아바타(초기값·이모지 캐릭터·사진 업로드) 변경, 이메일 변경(현재 비밀번호 재확인 필요), 비밀번호 변경
- 회원 탈퇴(비밀번호 확인) — 로그인 차단 + 이름/이메일/아바타 익명화, 과거 메시지 발신자 표시도 "탈퇴한 사용자"로 갱신, 1년 뒤 메시지 자동 파기(첨부파일 제외)
- 아이디 중복 확인, "아이디 기억하기"/"로그인 상태 유지"

**팀(워크스페이스)**
- 한 계정이 여러 팀에 속할 수 있고, 채팅방·멤버·검색·파일이 전부 팀 단위로 나뉩니다
- 로그인 직후(또는 "로그인 상태 유지"로 앱을 다시 켰을 때) 팀 선택 화면 → "팀으로 가기"로 진입
- 창 왼쪽 위의 팀 아이콘+팀명을 누르면 다른 팀으로 바로 전환하거나 팀 목록으로 돌아갈 수 있음
  (환경설정 "팀 전환 방식"에서 **드롭다운**(기본)과 속한 팀을 전부 한 줄 탭으로 펼쳐 보여주는
  **탭** 중에서 고를 수 있습니다). 팀을 바꾸면 이전 팀 방을 열어둔 채팅 화면은 닫히고 새 팀의
  "○○팀입니다" 시작 화면으로 돌아갑니다
- 다른 팀에서 온 메시지도 실시간으로 받고(안읽음/알림 반영), 그 방을 열면 해당 팀으로 자동 전환
- 팀 생성(만든 사람이 소유자), 팀 이름·아이콘 변경, 토픽 생성 권한 설정
- 계정 등급(관리자/정회원/준회원, 서버 운영자만 변경) + 팀 소유자 — 부서·직책 관리, 관리자의
  콘텐츠 삭제, 소유권 이양, 팀 삭제까지 서버에서 강제됩니다. 가입하면 준회원으로 시작합니다.
  자세한 내용은 [팀과 권한 등급](#팀과-권한-등급) 참고

**채팅방**
- 토픽(공개/비공개), 그룹, 1:1 DM 세 종류 — 모두 특정 팀에 속함
- 공개 토픽은 그 팀의 팀원 전원 자동 참여(팀에 새로 들어온 사람도 자동 포함, 준회원은 제외),
  비공개 토픽/그룹은 초대제
- 채팅방 목록 탐색(`/rooms/browse`), 멤버 초대, 나가기(DM은 "숨기기"), 즐겨찾기, 알림 끄기(뮤트)
- DM은 한쪽이 나갔다가 다시 말을 걸면 자동으로 되살아남(같은 방 재사용)

**메시징**
- 텍스트/이미지/파일/이모티콘(스티커) 전송, 이미지는 업로드 시 썸네일 별도 생성
- 첨부는 보내는 즉시 로컬 썸네일+용량+업로드 진행률(%)을 채팅/댓글 목록에 바로 보여주고, 업로드
  중에는 취소할 수 있음(채팅 입력칸/댓글 입력칸 둘 다, 최대 1GB)
- Windows에서 파일 탐색기의 이미지/파일을 채팅·댓글 입력칸에 드래그앤드롭으로 첨부 가능
- 본인 메시지·댓글 수정/삭제(소프트 삭제) — 허용 여부와 허용 시간(기본 5분, 최대 7일)은 팀
  설정([메시지 설정](#메시지-설정))을 따릅니다. 팀의 소유자·관리자는 자신이 참여 중인 방(비밀
  대화 제외)에서 같은 시간 안에 남의 메시지·댓글도 **삭제**할 수 있습니다(수정은 불가)
- 메시지별 댓글(스레드) — PC는 옆 패널, 모바일은 전체화면
- 메시지 인용 공유(다른 방으로), 메시지 전달
- 방별 안읽음 개수, 읽음 시각 동기화(`room:read`)
- 메시지 페이지네이션(기본 50개, 최대 200개, `before` 커서로 과거 메시지 추가 로드)
- 전체 채팅방 통합 검색(`/search` — 내가 속한 방으로 결과 범위 강제, 비밀 대화는 제외)

**비밀 대화 (종단간 암호화 E2EE, 1:1 전용)**
- 기기별 신원키(X25519 교환용 + Ed25519 서명용) 생성/등록, 개인키는 기기 밖으로 나가지 않음(`flutter_secure_storage`)
- 요청 → 수락/거절 다이얼로그(오프라인이었어도 다시 로그인 시 놓친 초대 복구), 임시 공개키 서명 검증(중간자 공격 방지)
- 서버는 암호문·공개키·서명만 보관 — 평문/공유비밀/체인키는 절대 서버에 오지 않음
- 재키잉(rekey) 제안/수신
- 메시지별 자동 삭제 타이머(1초~1주, 상대가 읽은 시점부터 카운트, 만료 시 첨부파일까지 완전 삭제)
- 대화 생명주기 시스템 메시지("요청 보냄"/"시작됨"/"상대방이 종료함") + 토스트(거절/양쪽 나가기)
- 채팅 목록·채팅방 제목에 초록 자물쇠 아이콘 + 초록 이름, 알림 미리보기는 항상 고정 문구, 통합 검색에서 제외

**서버 운영(관리자 콘솔)**
- 서버 운영자 개념(팀 등급과 별개) — 첫 가입자가 운영자가 되고, 이후 운영자가 지정
- 회원 관리: **계정 등급 지정**, 부서·직책, 계정 정지·해제, 모든 기기 강제 로그아웃
  (비밀번호 초기화 대행은 계정 탈취 위험 때문에 의도적으로 제공하지 않습니다)
- 팀 관리: 서버의 모든 팀 조회, 팀 생성 권한(정회원/관리자/서버 운영자), 부서·직책 관리 범위
- 감사 로그: 관리자 권한으로 한 일(메시지 삭제, 등급 변경, 계정 정지 등)을 전부 기록
- 운영 현황: 회원·팀·방·메시지 수, 오늘 활동량, 업로드 용량

**알림**
- FCM 푸시(Android 전용 — Windows는 미지원, 코드에서 `Platform.isAndroid`로 분기): 소켓이 붙어 있지 않은(=완전히 종료된) 기기에만 발송, data-only 페이로드를 클라이언트가 직접 렌더링
- 안드로이드 "대화" 스타일 알림(발신자 아바타 아이콘 포함), 뮤트한 방은 발송 안 함
- 방을 이미 보고 있으면 로컬 알림 억제, 알림 탭 시 해당 방으로 이동
- 알림 제목에 **팀 이름 배지**가 붙습니다(예: `홍길동 [1:1] [영업팀]`) — 여러 팀 알림이 섞여도 어느 팀인지
  바로 구분됩니다. 앱이 켜져 있을 때의 로컬 알림과 꺼져 있을 때의 FCM 푸시가 같은 모양입니다
- PC는 새 메시지가 오면 **작업표시줄 버튼이 창을 열 때까지 계속 깜빡입니다**(Windows가 기본 3회만
  깜빡이고 멈추므로 창이 앞으로 올 때까지 다시 걸어줍니다)

**서버 연결 / 배포**
- 자체 서명 TLS 인증서 + 클라이언트 인증서 핀닝(공인 CA 미사용)
- 페어링 코드(4자리, 5분 유효, 1회용)로 앱 재빌드 없이 새 인증서 발급/서버 이전
- **초대 링크**(설치→가입, 서버 운영자·계정 관리자·팀 소유자가 발급) — [초대 링크](#초대-링크-설치가입) 참고
- **팀 초대 링크**(설치+가입+팀 자동 합류+등급 자동 부여, 서버 설정이 정한 등급 이상만 발급) —
  [팀 초대 링크](#팀-초대-링크자동-합류등급-부여) 참고
- 서버 버전 배너(`/version`) + 앱 안에서 바로 다운로드/설치
- Windows 설치 프로그램(Inno Setup), Android APK 배포 스크립트(`publish_release.ps1`)

**클라이언트 UX**
- 다크/라이트/시스템 테마, Windows 시스템 시작 시 자동 실행, 다운로드 위치 지정
- 이미지 뷰어(확대/축소), 스티커 선택기, 날짜 구분선, 안읽음 뱃지, 즐겨찾기 별표

## 팀과 권한 등급

사내 메신저이므로 모든 대화는 **팀(워크스페이스)** 단위로 나뉩니다. 한 계정이 여러 팀에 속할 수
있고, 채팅방·멤버·검색·파일은 지금 보고 있는 팀 안에서만 보입니다(서버가 모든 요청에서
`teamId`로 범위를 강제합니다 — `server/src/teams.js`, `server/src/rooms.js`). 예외로 **조직도**
(팀 목록 화면의 아이콘, 계정 등급 관리자 이상만 보임)는 팀과 무관하게 서버 전체 팀/회원을
보여줍니다 — "팀" 탭은 팀별로 묶어서(누르면 그 자리에 멤버가 펼쳐짐), "멤버" 탭은 서버 전체
회원을 검색합니다. 멤버를 눌러 1:1 메시지를 시작할 수도 있지만, 평문 DM은 팀 안에서만 만들 수
있어서 나와 그 사람이 함께 속한 팀이 있을 때만 버튼이 활성화됩니다(비밀 대화는 그 제약이 없음).

**팀에 들어가는 방법**

- **팀 생성** — 팀을 만든 사람이 그 팀의 **소유자**가 됩니다(별도의 설치용 소유자 비밀번호는 없음).
- **팀에 가입시켜 주기** — 회원가입만 한 계정은 아직 어느 팀에도 속하지 않습니다. 소유자·관리자가
  팀 설정 → "팀원 추가"에서 등급을 정해 팀에 넣어 줍니다. 팀에 들어오면 그 팀의 공개 토픽에
  자동으로 참여됩니다(준회원 제외).

### 권한 등급

등급은 **계정에 붙습니다**(`users.role`). 어느 팀에 있든 같은 등급이고, **서버 운영자만**
[관리자 콘솔](#서버-운영자와-관리자-콘솔)에서 바꿀 수 있습니다. 팀 단위로 남은 것은 "그 팀의
소유자인지"뿐입니다. 등급을 바꾸면 그 회원이 로그인해 있는 동안에도 **즉시 반영**됩니다 —
서버가 소켓으로 `user:role-updated` 이벤트를 보내면 클라이언트가 `/users/me`를 다시 불러오므로,
재로그인 없이 바로 새 등급의 화면(버튼 노출 등)으로 바뀝니다.

| 등급 | 코드값 | 요약 |
|---|---|---|
| 관리자 | `admin` | 자기가 속한 **모든 팀**의 설정·팀원·콘텐츠 관리 + 방·팀 만들기 |
| 정회원 | `member` | 방 만들기·참여·대화 등 일반 협업 기능 전부 |
| 준회원 | `guest` | 초대받은 방에서만 활동(방 생성·토픽 참여·대화 시작 불가) |

**회원가입하면 준회원으로 시작합니다.** 서버 운영자가 정회원 이상으로 올려줘야 방을 만들거나
공개 토픽에 참여할 수 있습니다(사내 메신저에서 가입만 한 사람이 바로 활동하지 않도록 하는
의도적인 온보딩 흐름입니다). 서버의 **첫 계정**만 예외로 관리자 + 서버 운영자로 시작합니다.

**팀 소유자**

팀을 만든 사람이 그 팀의 소유자가 되고(`team_members.role = 'owner'`), 소유권은 넘길 수
있습니다. 소유자만 할 수 있는 일: **팀 삭제**, **소유권 이양**, **관리자를 팀에서 빼기**.
소유자는 팀에서 뺄 수 없습니다.

**팀을 관리할 수 있는 사람** = 그 팀의 **소유자** 또는 계정 등급이 **관리자**인 사람.
할 수 있는 일:
- 팀 설정: 팀 이름·아이콘 변경, 토픽 생성 권한, [메시지 설정](#메시지-설정),
  팀원의 부서·직책 관리
- 팀원 추가/제외 — **등급은 여기서 정하지 않습니다**. 각자가 이미 가진 계정 등급 그대로
  팀에 들어오고, 팀 설정의 "팀원 추가" 목록에는 프로필 사진·이름·등급이 표시만 됩니다.
- 콘텐츠 관리: 남의 메시지·댓글 삭제(아래 조건을 모두 만족할 때, 팀이 정한 수정/삭제 가능
  시간 안에서만):
  1. 그 팀의 소유자이거나 계정 등급이 관리자이고,
  2. **그 방의 멤버**이며 — 초대받지 않은 비공개 토픽/그룹/1:1 대화는 관리자도 볼 수 없고
     관리할 수 없습니다,
  3. **비밀 대화(E2EE)가 아님** — 서버가 내용을 볼 수 없는 대화라 관리 대상이 아닙니다.

  남의 글 **수정**은 소유자·관리자·서버 운영자를 포함해 **누구도** 할 수 없습니다.

**준회원(guest)이 못 하는 것**

- 토픽/그룹 방 생성, 공개 토픽 탐색·참여(자동 참여 대상도 아님)
- 1:1 대화를 **먼저 시작하기**(반대로 다른 사람이 준회원에게 말을 거는 것은 됩니다)
- 팀 생성, 멤버 초대
- 클라이언트에서도 해당 버튼(+ 방 만들기, 토픽 찾기, 1:1 메시지, 멤버 초대)이 아예 보이지 않습니다.
- 나중에 정회원 이상으로 올라가면, 그동안 빠져 있던 소속 팀들의 공개 토픽에 자동으로 참여됩니다.

**토픽 생성 권한**은 팀 설정(팀을 관리할 수 있는 사람이 정함)에서 팀마다 따로 정합니다 —
정회원 이상(기본) / 관리자 이상 / 소유자만 / **지정**(팀을 관리할 수 있는 사람이 정회원 이상
중에서 콕 집어 고른 특정 팀원들만, 여러 명 가능 — `teams` 테이블의 `topic_creators`).
준회원은 어느 설정에서도 토픽을 만들 수 없습니다. **그룹채팅은 이 설정과 무관하게 항상
정회원 이상이면 만들 수 있습니다** — 토픽은 팀 전체에 공개되는 채널이라 만드는 사람을 제한할
수 있어야 하지만, 그룹은 만든 사람이 스스로 고른 소수만 들어오는 사적인 대화라 제한할 이유가
약하기 때문입니다. 이미 있는 방(토픽·그룹)에 나중에 멤버를 추가로 초대하는 것도 이 설정과
무관하게 정회원 이상이면 누구나 할 수 있습니다.

**팀 생성 권한**은 서버 설정으로 정합니다 — 정회원 이상(기본) / 관리자 이상 / 서버 운영자만
([운영 현황](#운영-현황) 참고). 서버 운영자는 설정과 무관하게 항상 만들 수 있습니다. **팀 초대
링크 생성 권한**도 같은 방식의 별도 서버 설정입니다 —
[팀 초대 링크](#팀-초대-링크자동-합류등급-부여) 참고.

### 메시지 설정

팀 설정 → 팀 정보 → **[메시지 설정]** 에서 소유자·관리자가 정합니다.

| 설정 | 값 | 설명 |
|---|---|---|
| 메시지 수정/삭제 | ON(기본) / OFF | OFF면 그 팀에서는 **아무도**(소유자·관리자 포함) 메시지·댓글을 고치거나 지울 수 없습니다. 대화 기록을 그대로 남겨야 하는 팀을 위한 스위치입니다. |
| 수정/삭제 가능 시간 | 5분(기본) / 30분 / 1시간 / 24시간 / 7일 | 작성 후 이 시간 안에서만 수정·삭제할 수 있습니다. **본인 메시지든 관리자의 콘텐츠 관리든, 수정이든 삭제든 똑같이 적용**됩니다. |

- 기본값(ON / 5분)은 이 설정이 생기기 전 코드에 박혀 있던 값과 같아서, 아무것도 건드리지 않으면
  동작이 그대로입니다.
- **수정과 삭제의 유일한 차이**: 남의 글은 관리자가 **삭제만** 할 수 있고, **수정은 누구도**
  (소유자·관리자 포함) 할 수 없습니다 — 남의 말을 고치는 것은 내용 위조가 되기 때문입니다.
- 판정은 서버 `server/src/moderation.js`의 `canModifyContent` 한 곳에서 하고, 메시지·댓글의
  수정·삭제 네 경로가 모두 같은 함수를 씁니다. 클라이언트는 시간이 지났거나 설정이 꺼져 있으면
  메뉴 항목 자체를 감춥니다.

### 부서 / 직책

**팀 단위**로 둘지 **계정 단위**로 둘지 서버 운영자가 관리자 콘솔 "운영 현황" → **팀·직책
관리**에서 고릅니다(기본: 팀 단위).

| 설정 | 저장 위치 | 정하는 곳 |
|---|---|---|
| 팀 단위(기본) | `team_members.department`/`position` | 각 팀의 팀 설정 → 멤버(그 팀을 관리할 수 있는 사람) → "직책 수정". 아래 "직책 목록" 중에서 자신의 직책과 같거나 그 아래만 칩으로 골라 부여할 수 있습니다 — 부서는 이 화면에 입력칸이 없습니다(자유 입력 칸을 없앴습니다, 기존 값은 컬럼에 남아있을 뿐 이 흐름으로는 더 이상 바뀌지 않습니다) |
| 계정 단위 | `users.department`/`position` | 관리자 콘솔 → 회원(서버 운영자 — 목록 전체에서 제한 없이 선택) 또는 각 팀의 팀 설정 → 멤버(그 팀을 관리할 수 있는 사람 — 위와 같이 자신의 직책 이하만) |

팀 단위면 한 사람이 팀마다 다른 직책을 가질 수 있고(예: PST에서는 팀장, 개발1팀에서는 팀원),
계정 단위면 회사 조직도가 하나로 통일됩니다.

**직책 목록** — 서버 운영자가 관리하는 직책 후보 목록(`position_options` 테이블, 설치 직후
사원/주임/대리/과장/차장/부장/이사/대표가 이 순서로 기본 들어있습니다 — `sort_order`는
**작을수록 서열이 낮습니다**, 사원=0 … 대표=7). 관리자 콘솔 "운영 현황"에서 "+" 버튼(이름 입력
팝업)으로 추가하고 항목의 ×로 삭제하며, 항목을 끌어다 옮겨 서열(`sort_order`)도 바꿀 수
있습니다(끄는 동안 나머지 항목이 밀려나며 놓일 자리를 보여주고, 놓는 순간 전체 순서를 저장 —
조직에 맞게 순서를 다시 짜면 그게 곧 새 서열이 됩니다). 목록 아래 "회원가입 시 기본 직책"
드롭다운에서 고른 직책이 "기본값"이 됩니다(최대 1개, `is_default`)
— **회원가입 시 이 직책이 자동으로 부여됩니다**(`server/src/auth.js`, 팀 단위 서버에서는 이
값이 당장 어디서도 안 쓰이지만 나중에 계정 단위로 바뀌어도 바로 의미가 생기도록 항상 채워
둡니다). 목록 자체는 `GET /api/position-options`로 서버 운영자가 아니어도 누구나 조회할 수
있어서, 관리자 콘솔의 "직책 수정"·팀 설정의 "직책 수정"·"팀 초대 링크"의 "부여할 직책"이 모두
같은 목록을 씁니다.

**"자신의 직책 이하만" 규칙** — 관리자 콘솔의 "직책 수정"(서버 운영자 전용)을 뺀 나머지
세 곳(팀 설정의 "직책 수정", 프로필 카드의 "직책 수정" 연필 버튼, "팀 초대 링크"의 "부여할
직책")은 전부 **자신의 직책과 같거나 그 아래만** 남에게 부여할 수 있습니다 —
나보다 높은 직책을 남에게 주는 권한 상승을 막기 위해서입니다(등급의 "자신보다 높은 등급은
부여 불가" 규칙과 같은 이유). 서버도 매 요청마다 같은 규칙으로 다시 확인합니다
(`server/src/teams.js`의 `PATCH /teams/:id/members/:userId`, `server/src/teamInvites.js`).
자신의 직책이 목록에 없으면(미등록 등) 아무 직책도 새로 부여할 수 없습니다.

이 기능이 생기기 전부터 있던 값(목록에 없는 값, 또는 지금은 서열 제한에 걸리는 값)은 그대로
저장되어 있는 한 유지되고, 다이얼로그에 "(목록에 없는 기존 값)" 칩으로 표시되어 그대로
저장하거나 목록의 다른 값으로 바꿀 수 있습니다 — 실제로 **바꾸려는** 값만 검사합니다
(`server/src/admin.js`의 `PATCH /admin/users/:id/org`, `server/src/teams.js`의 위 라우트).

**프로필 카드**(다른 사람 것/내 것)에는 부서 대신 그 사람이 실제로 속한 **팀** 이름과 **직책**이
"이름" 아래 표시됩니다. 팀 단위 설정이면 팀마다 직책이 다를 수 있어 "PST · 팀장"처럼 팀별로
짝지어 보여주고, 계정 단위면 "팀" 목록과 "직책" 하나를 따로 보여줍니다. 소유자·관리자만 직책을
고칠 수 있고(연필 아이콘), 팀 소속 자체는 이 카드에서 바꿀 수 없습니다(팀 설정의 "팀원
추가/제외"에서만). 다른 사람의 "팀" 항목은 `GET /api/users/:id/teams`가 내려주는데, 노출
범위가 대상에 따라 다릅니다 — 대상이 계정 등급 **관리자**면 나와 함께 속한 팀만, **정회원·
준회원**이면 그 사람의 전체 소속 팀을 보여줍니다(본인이 자기 프로필을 볼 때는 항상 전체).
"조직도" 화면의 "팀" 탭은 이 API가 아니라 관리자 전용 `GET /api/org-chart/teams`를 그대로
쓴다는 점에서 다릅니다.

### 권한 규칙이 정의된 곳

등급 판정 규칙은 서버 `server/src/permissions.js` 한 곳에 모여 있고(`canManageTeam`,
`canCreateRooms`, `canBrowseTopics`, `canInviteMembers`, `canModerateContent`, `canCreateTeam`),
라우터들은 반드시 이 함수를 통해서만 판단합니다. "계정 등급 + 그 팀의 소유자 여부"를 한 번에
모아오는 `server/src/access.js`의 `teamAccess()`가 그 입력을 만듭니다.

클라이언트 `client/lib/models/team.dart`의 `AccountRole`과 `Team.canManage()`가 같은 규칙을
복제하고 있지만 이는 **버튼을 감추기 위한 힌트일 뿐**이며, 실제 차단은 언제나 서버가 합니다.

이 등급들은 전부 **팀 안에서만** 의미가 있습니다. 서버 전체를 다루는 권한은 따로 있습니다 —
[서버 운영자와 관리자 콘솔](#서버-운영자와-관리자-콘솔) 참고.

## 초대 링크(설치→가입)

새 팀원에게 "이 링크 열어서 설치하고 가입하세요"라고 보낼 수 있는 링크입니다. **팀 합류는
포함하지 않습니다** — 회원가입은 원래 누구나 열려 있고(초대 없이도 가입 가능), 팀에 넣는 일은
지금처럼 항상 소유자·관리자가 팀 설정 → 팀원 추가에서 수동으로 합니다. 이 링크가 실제로 하는
일은 **낯선 기기가 이 서버(자체 서명 인증서)를 신뢰하게 만드는 것** 하나뿐이고, 기존 [페어링
코드](#서버-실행-방법) 메커니즘을 그대로 재사용합니다.

**만들 수 있는 사람**: 서버 운영자, 계정 등급이 관리자인 사람, 또는 어느 팀이든 소유자인 사람
(`server/src/permissions.js`의 `canCreateInviteLink`). 삼선(계정) 메뉴 → **"초대 링크 생성"**
에서 만듭니다 — 관리자 콘솔과 달리 이 메뉴는 서버 운영자가 아닌 팀 소유자에게도 보입니다.

**만드는 값**: 메모(선택, 예: "9월 신입")뿐입니다 — 유효기간은 고르지 않고 항상 **발급 후
7일**로 고정입니다(`server/src/invites.js`의 `INVITE_EXPIRY_DAYS`). 생성하면 링크가 자동으로
클립보드에 복사되어 카카오톡·이메일 등 원하는 곳에 바로 붙여넣어 보낼 수 있습니다. 페어링
코드(4자리, 5분, 1회용)와 달리 이 링크의 코드는 사람이 직접 입력할 일이 거의 없어(복사 +
붙여넣기, 또는 아래 딥링크 자동입력) 훨씬 길고(96비트 무작위) 오래 살아있으며, **1회용이
아닙니다** — 유효기간 안에서는 여러 기기(예: 이번 달 입사한 신입 여러 명)가 같은 링크를 나눠
받아도 됩니다. 만든 사람은 목록에서 언제든 취소(폐기)할 수 있습니다.

**상대방이 받는 경험**:
1. 링크를 열면 평문 HTTP 안내 페이지가 뜹니다(자체 서명 인증서 경고가 뜨지 않습니다 — 페어링과
   같은 평문 포트인 `PAIRING_PORT`를 씁니다). 이 페이지는 열리자마자 `tangotalk://` 커스텀
   스킴으로 앱을 열어보려고 시도합니다 — TangoTalk이 이미 설치돼 있다면 곧바로 앱이 뜨면서 아래
   3번 단계(서버 주소/코드 입력)까지 자동으로 끝납니다.
2. 설치돼 있지 않으면(=페이지가 그대로 남아있으면) Windows/Android 설치 버튼으로 설치 파일을
   받습니다(같은 평문 포트로 스트리밍 — 여기서도 브라우저 경고가 없습니다). **설치가 끝나면
   같은 초대 링크를 다시 눌러야 합니다** — 그래야 이번엔 막 설치된 앱이 커스텀 스킴을 잡아채
   실행됩니다.
3. 앱이 `tangotalk://pair/?address=...&code=...`로 열리면 로그인 화면의 **"서버 주소
   변경"**(첫 실행이면 서버 연결 화면)이 서버 주소와 코드를 미리 채운 채로 뜹니다 — 연결
   버튼은 직접 눌러야 합니다(자동 연결은 하지 않음). 딥링크가 안 먹히는 환경(예: 링크를 다른
   기기로 옮겨 열었을 때)을 위해 안내 페이지에는 주소/코드를 직접 복사해 붙여넣는 방법도 접이식
   섹션으로 남아 있습니다 — 이 입력칸은 4자리 페어링 코드와 초대 링크의 코드를 똑같이
   받습니다(길이로 서버가 구분합니다).
4. 회원가입(초대 없이 열려 있음) → 팀 소유자·관리자에게 팀 참가를 요청합니다.

**딥링크 등록**(`tangotalk://` 커스텀 스킴 — 고정 도메인이 없는 LAN 자체 호스팅 구조라 도메인
소유 검증이 필요한 HTTPS App Links 대신 이 방식을 씁니다):
- **Android**: `AndroidManifest.xml`의 `MainActivity`에 `tangotalk` 스킴 `intent-filter`를 선언.
  앱이 이미 떠 있으면 OS가 알아서 그 인스턴스로 새 인텐트를 전달합니다.
- **Windows**: 설치 프로그램(`client/windows/installer/messenger.iss`)이 `HKCU\Software\Classes\tangotalk`에
  프로토콜 핸들러를 등록합니다(관리자 권한 불필요 — `PrivilegesRequired=lowest`와 동일 원칙).
  앱이 이미 떠 있는 상태에서 링크를 다시 열면 `app_links` 패키지의 `SendAppLinkToInstance()`가
  기존 창을 찾아 링크를 넘기고 포그라운드로 가져옵니다(`windows/runner/main.cpp`).

**만료·취소된 링크**를 열면 안내 페이지에 "만료되었습니다 / 취소되었습니다" 문구만 뜨고
설치 버튼이 사라지며, 설치 파일 다운로드와 `/pair/<코드>` 인증서 발급도 함께 막힙니다 —
링크 하나가 통째로 죽는 단순한 규칙입니다.

## 팀 초대 링크(자동 합류+등급 부여)

위 [초대 링크](#초대-링크-설치가입)와 달리, 이 링크로 **가입하면 그 즉시 지정한 팀에 자동으로
합류하고 지정한 계정 등급까지 함께 부여**됩니다. 서버 운영자가 신입이 가입할 때마다 일일이
등급을 올려주고 팀에 넣어주는 수고를 줄이기 위한 기능입니다(`server/src/teamInvites.js`,
`server/src/db/schema.js`의 `teamInviteLinks` 테이블).

**만들 수 있는 사람**: 서버 설정 **"팀 초대 링크 생성 권한"**이 정한 등급 이상 —
[운영 현황](#운영-현황) 참고(기본값: 관리자 이상). 이 링크는 팀 합류와 계정 등급을 함께
부여하므로, 팀 합류만 시켜주는 [초대 링크](#초대-링크-설치가입)(팀 소유자면 누구나 가능)보다
기본이 더 보수적입니다. 권한이 있으면 팀 설정 → 팀 정보에 **"팀 초대 링크 생성"** 버튼이
나타납니다(`session.canCreateTeamInviteLink` — 서버가 `/users/me` 응답에 미리 계산해서
내려줍니다). 이미 어느 팀인지 정해진 화면이라 팀 선택이 그 팀으로 미리 맞춰집니다.

**만드는 값**: 팀(내가 속한 팀 중에서 고름), 부여할 등급(준회원/정회원/관리자), 부여할
직책(선택 — 직책 목록에서 고름), 메모(선택). **등급/직책 모두 내 것보다 높을 수 없습니다**
— 정회원도 이 링크를 만들 수 있는 서버 설정이라면, 정회원이 남에게 관리자 등급이나 더 높은
직책을 부여하는 링크를 만드는 권한 상승을 막기 위해서입니다(서버 운영자는 등급 제한의
예외 — 관리자 콘솔에서 이미 자유롭게 등급을 바꿀 수 있는 사람이므로). 직책은 직책 목록
(`GET /api/position-options`, 서버 운영자가 아니어도 조회 가능)에서 서열순으로 불러와,
내 직책과 같거나 그 아래만 고를 수 있게 걸러서 보여주고, 서버도 같은 규칙으로
한 번 더 확인합니다(`server/src/teamInvites.js`). 유효기간은 초대 링크와 마찬가지로 발급 후
**7일** 고정(`TEAM_INVITE_EXPIRY_DAYS`)이고, 여러 사람이 나눠 쓸 수 있는 다회용 링크입니다.
만든 사람은 목록에서 언제든 취소할 수 있습니다.

**상대방이 받는 경험**: 설치→딥링크→서버 연결까지는 [초대 링크](#초대-링크-설치가입)와
완전히 같은 흐름(`tangotalk://pair/?address=...&code=...`, 같은 평문 안내 페이지 구조)을
그대로 재사용합니다. 차이는 마지막 단계뿐입니다 — **회원가입을 완료하는 순간** 서버가 이
코드를 팀 초대 링크로 인식해 지정한 팀에 팀원(일반 멤버)으로 추가하고, 계정 등급을 지정한
값으로 바꾸고, 직책을 지정했다면 그 값도 계정에 채워 넣고(부서·직책 관리 범위가 '팀
단위'라도 값 자체는 항상 채워둡니다 — "계정 단위"로 바뀌면 바로 의미가 생기도록), 등급이
준회원이 아니면 그 팀의 공개 토픽에도 자동 참여시킵니다(`server/src/auth.js`의
`/register`). **이미 계정이 있는 사람이 이 링크를 열어도 자동 합류는 일어나지 않습니다**
— 새로 가입할 때만 적용되는 일회성 효과이고, 유효하지 않거나 만료된 코드는 조용히
무시되어 회원가입 자체는 항상 정상적으로 끝납니다.

## 서버 운영자와 관리자 콘솔

팀 등급(소유자/관리자/…)과 **완전히 별개의 축**으로, 서버 전체를 운영하는 **서버 운영자**가
있습니다(`users.is_server_admin`). 팀 관리자는 자기 팀 안만 볼 수 있지만, 서버 운영자는 회원·팀·
감사 로그·사용량을 서버 단위로 봅니다.

**운영자가 되는 방법**

- **기존 서버**: 마이그레이션(`0020`)이 가장 먼저 가입한 계정에 표시를 찍습니다(1단계에서 PST 팀
  소유자를 정한 것과 같은 규칙).
- **새 서버**: 첫 가입자가 자동으로 운영자가 됩니다(`auth.js`의 `hasNoServerAdmin`).
- 이후에는 운영자가 관리자 콘솔에서 다른 사람을 지정/해제합니다. **마지막 운영자는 해제할 수
  없습니다**(아무도 콘솔에 못 들어가는 상태를 막기 위해).

**여는 곳**: 삼선 메뉴 → **"서버 관리"**(모바일은 더보기 탭). 운영자에게만 보이고, 서버가 매
요청마다 다시 확인하므로 화면이 열려 있다는 것만으로 권한이 생기지는 않습니다.

### 운영 현황

회원·팀·대화방·전체 메시지 수, 오늘 올라온 메시지+댓글, 업로드 폴더 총 용량, 서버 시작 시각.
여기서 서버 전체 설정 두 가지도 정합니다:

| 설정 | 값 | 설명 |
|---|---|---|
| 팀 생성 권한 | 정회원(기본) / 관리자 / 서버 운영자 | 팀을 새로 만들 수 있는 최소 계정 등급. 준회원은 어느 값이든 불가하고, 서버 운영자는 설정과 무관하게 항상 가능합니다. |
| 팀 초대 링크 생성 권한 | 정회원 / 관리자(기본) / 서버 운영자 | [팀 초대 링크](#팀-초대-링크자동-합류등급-부여)를 만들 수 있는 최소 계정 등급. 팀 합류+등급 부여를 함께 하는 기능이라 팀 생성 권한보다 기본값이 더 보수적입니다. |
| 팀·직책 관리 | 팀 단위(기본) / 계정 단위 | [부서 / 직책](#부서--직책) 참고. 계정 단위면 바로 아래 "직책 목록"도 여기서 관리합니다. |

### 회원 관리

전체 회원(탈퇴 포함)을 이름·아이디로 검색하고, 각자의 상태와 소속 팀을 봅니다.

| 동작 | 효과 |
|---|---|
| **계정 등급 변경** | 준회원/정회원/관리자. **여기가 등급을 바꾸는 유일한 곳**입니다(팀 설정에서는 못 바꿉니다). 준회원 → 정회원 이상으로 올리면 그 사람 소속 팀들의 공개 토픽에 자동으로 넣어줍니다. 대상이 로그인해 있으면 재로그인 없이 **바로** 반영됩니다(소켓 `user:role-updated` 이벤트). |
| 직책 수정 | "팀·직책 관리"가 계정 단위면 운영 현황의 "직책 목록"을 가로로 늘어놓은 칩 중에서, 팀 단위면 자유 입력으로 직책을 고칩니다(팀 소속 자체는 여기서 못 바꿉니다 — 회원 목록에 이미 팀 칩으로 표시되고, 바꾸려면 각 팀의 팀 설정 "팀원 추가/제외"에서 합니다). |
| 계정 정지 / 해제 | 정지되면 로그인·토큰 재발급·소켓 연결이 모두 막히고, 이미 붙어 있던 기기도 즉시 끊깁니다. 탈퇴와 달리 되돌릴 수 있고 이름/메시지는 그대로 남습니다. 자기 계정은 정지할 수 없습니다. |
| 모든 기기에서 로그아웃 | `token_version`을 올려 기존 토큰을 전부 무효화합니다. 다시 로그인하면 정상 사용 가능합니다. |
| 서버 운영자 지정 / 해제 | 관리자 콘솔 접근 권한을 주고 뺍니다. |

> **비밀번호 초기화 대행은 의도적으로 없습니다.** 운영자가 남의 평문 비밀번호를 직접 정할 수
> 있게 하면 그 계정을 완전히 탈취할 수 있는 힘을 갖게 되므로, 이 기능은 제공하지 않습니다.
> 계정에 문제가 있으면 계정 정지나 강제 로그아웃으로 대응하고, 비밀번호 자체는 본인만
> 회원가입 때 등록한 보안 질문으로 재설정할 수 있습니다(`POST /auth/reset-password`).

### 팀 관리

서버의 **모든** 팀을 봅니다(운영자가 속하지 않은 팀 포함) — 이름·아이콘·인원수·만든
사람·생성일. 팀 자체의 설정 변경/삭제는 지금도 그 팀의 소유자만 할 수 있습니다.

### 감사 로그

**관리자 권한으로 한 일**만 추가 전용으로 기록합니다(일반 대화는 메시지 자체가 기록이므로 남기지
않습니다). 계정이나 팀이 지워져도 로그가 남도록, 그 시점의 이름을 스냅샷으로 함께 저장합니다.

기록되는 행위: 남의 메시지·댓글 삭제, 팀원 추가·제외, 등급/부서·직책 변경, 소유권 이양, 팀 삭제,
계정 정지·해제, 강제 로그아웃, 서버 운영자 지정·해제, 서버 설정 변경.
행위 종류로 걸러 보거나 50건씩 페이지를 넘겨 볼 수 있습니다.

> 기록 실패가 원래 동작을 막지는 않습니다 — 로그를 못 남겼다고 메시지 삭제가 실패하면 더 나쁘기
> 때문에, 오류는 서버 콘솔에만 남기고 넘어갑니다(`server/src/audit.js`).

## 프로젝트(업무 관리)

토픽(대화방)이 "주제별 대화"라면, **프로젝트**는 "업무를 계획·추적하는 공간"입니다. 대화방과
완전히 별개의 테이블이라 방 목록·검색·파일에는 섞이지 않고, 팀에 속하며 초대된 구성원만 볼 수
있습니다. PC 앱 상단 툴바의 과녁 아이콘(알림 센터 왼쪽, 구분선으로 구분)으로 엽니다.

### 화면 구성

큰 대화상자 하나 안에서 왼쪽 사이드바와 오른쪽 내용이 함께 움직입니다.

| 사이드바 | 내용 |

| 필터·필드 열 | 프로젝트 화면 탭 줄 오른쪽 "필터링" — 누르면 그 자리에 펼쳐지고 고르는 즉시 목록에 반영됩니다. 빠른 필터링(미완료/완료된/지연/내 업무) 칩과 상태·담당자(담당자 없음 포함)·유형·우선순위, 그리고 "필터 추가"로 꺼내 쓰는 사용자 정의 필드(선택 필드는 값 일치, 텍스트 필드는 포함, 숫자/진행률·날짜 필드는 최소~최대)를 조합해 리스트/칸반/간트/캘린더에 똑같이 적용. 걸린 조건은 탭 줄 아래 칩으로 남고 칩의 ×로 하나씩 뺍니다(활성 개수 표시, "지우기"로 전체 해제). 리스트 표에는 사용자 정의 필드마다 열이 붙습니다 |
| 프로젝트 종료(보관) | 톱니 버튼 → "삭제" → "프로젝트 종료"(담당자·팀 소유자/관리자). 종료하면 사이드바 "종료된 프로젝트"로 옮겨지고 읽기만 가능(업무·댓글·노트 쓰기는 409로 거부, 마감 알림 중지, 내 업무/캘린더/간트/홈 통계에서 빠짐). "다시 시작"으로 되돌리며, 데이터는 그대로 남습니다 |
| 캘린더 · 간트차트 · 노트 | 자리만 잡아둔 상태(다음 단계) |
| 프로젝트 목록 | 대표 색상 점이 붙은 즐겨찾기(별)와 나머지. 고르면 그 프로젝트의 업무를 상태별로 묶어 보여줍니다. "공개 프로젝트 찾기"로 아직 안 들어간 공개 프로젝트를 보고 초대 없이 "참여"할 수 있습니다 |

**프로젝트 생성**(사이드바 `+`): 이름, 대표 색상(7색), 프로젝트 키(업무 번호 앞에 붙는 영문 식별자 — 예: `HR`, `DEV`), 설명, 공개 설정(공개/비공개)을 입력하고 "프로젝트 생성"을 누릅니다. 구성원은 만든 뒤 프로젝트 화면에서 초대합니다. **공개** 프로젝트는 팀의 정회원 이상이 초대 없이 확인하고 참여할 수 있고, **비공개**는 초대한 구성원만 볼 수 있습니다.

### 업무

- 제목·설명·담당자·**참조자(여러 명)**·**유형**·상태(할 일/진행 중/완료)·우선순위·시작일·마감일을 가집니다.
- **유형**(Bug/Feature/행사 등)은 프로젝트마다 이름과 색을 직접 관리합니다(프로젝트 화면 ⋮ 메뉴 → "업무 유형 관리", 프로젝트 담당자와 팀 소유자·관리자). 새 프로젝트에는 Bug/Feature/Improvement/기타가 기본으로 들어가고, 유형을 지워도 그 업무는 남고 유형만 비워집니다.
- **참조자**로 지정된 사람의 "내 업무"에도 그 업무가 나타납니다(홈 대시보드의 "내가 담당한 업무" 통계는 담당 업무만 셉니다).
- 화면에 보이는 번호(`MKT-1001`)는 **프로젝트 식별자 + 순번**입니다. 순번은 프로젝트가 직접
  들고 있어서(`projects.next_task_seq`) 업무를 지워도 번호를 재사용하지 않습니다.
- 마감일이 있으면 `D-2` / `D-DAY` / `D+1` 뱃지가 붙고, 지났는데 완료가 아니면 "지연"으로 셉니다.
- 업무 카드에 댓글을 달 수 있고, 최근 댓글은 홈 대시보드에 모입니다.

### 권한

- **만들기**: 서버 설정 "프로젝트 생성 권한"(관리자 콘솔 → 운영 현황)이 정한 최소 등급 —
  정회원 이상(기본) / 관리자 이상 / 서버 운영자만. 준회원은 어느 설정에서도 만들 수 없고,
  서버 운영자는 설정과 무관하게 항상 만들 수 있습니다(팀 생성 권한과 같은 구조).
- **참여**: 이미 만들어진 프로젝트에 초대받아 참여하는 것은 이 설정과 무관합니다(준회원도 초대받으면
  볼 수 있습니다).
- **설정·삭제·구성원 초대**: 프로젝트 담당자(만든 사람)와 그 팀의 소유자·관리자.

## 향후 계획 / 미구현 기능

코드베이스를 확인한 결과, 아래 기능은 **아직 구현되어 있지 않습니다**(추측 없이, 실제로 코드/이벤트가
없는 것만 적었습니다):

- **타이핑 표시**(상대가 입력 중임을 보여주는 기능) — 관련 소켓 이벤트 없음
- **서버 주소 변경 시 사용자 계정 유지** — 지금은 페어링/서버 주소 변경 흐름 자체는 있지만, 서버가
  완전히 다른 인스턴스로 바뀌면(DB가 다르면) 계정은 그 서버 기준으로 다시 로그인해야 합니다
- **채팅방 비밀번호/초대 링크** 등 별도 접근 제어 수단 — 지금은 서버에서 직접 멤버로 추가하는 방식뿐
- **웹 기반 관리자 화면** — 관리자 콘솔은 PC 앱 안에 있습니다([서버 운영자와 관리자
  콘솔](#서버-운영자와-관리자-콘솔)). 브라우저로 접속하는 별도 운영 화면은 없어서, 운영하려면
  앱을 깔아야 합니다
- **릴리즈 배포의 화면화** — 새 클라이언트/서버 버전을 배포하는 건 여전히 콘솔 스크립트
  (`publish_release.ps1`)로 합니다. DB 백업/복원은 시작 메뉴의 "백업"/"복원"으로 화면화됐습니다
- **서버 설치 프로그램 자체의 자동 업데이트** — 새 `tangotalk-server-setup.exe`를 만들어서 대상 PC에
  다시 실행해주는 건 됩니다(위 "새 서비스 PC에 네이티브 설치 프로그램으로 설치/업데이트" 참고),
  다만 그 배포/실행을 서버가 스스로 감지해서 알아서 받아 설치하는 건 아직 없습니다(관리자 권한
  작업이라 무인 자동 적용은 위험 부담이 있어 일부러 범위 밖으로 뒀습니다).

## 구성도

```
                          (LAN, HTTPS+WSS, TLS 핀닝)
 ┌───────────────┐  ────────────────────────────────▶  ┌─────────────────────────┐
 │ Flutter 클라이언트│                                     │ Node.js 서버 (server/)   │
 │  · Windows      │  ◀────────────────────────────────  │  Express + Socket.io    │
 │  · Android      │       평문 HTTP(PORT+1, 페어링 전용)   │  PORT=3000(기본)         │
 └───────┬─────────┘                                     └──────────┬──────────────┘
         │  FCM data-only push                                       │ drizzle-orm
         │  (Android, 앱 완전 종료 시만)                                │
         ▼                                                            ▼
 ┌───────────────┐                                     ┌─────────────────────────┐
 │ Firebase Cloud  │ ◀── firebase-service-account.json ──│      PostgreSQL          │
 │ Messaging       │      (서버가 발송 시 사용)             │  users/rooms/messages... │
 └───────────────┘                                     └─────────────────────────┘
```

- 클라이언트는 서버가 스스로 발급한 자체 서명 TLS 인증서만 신뢰합니다(공인 CA 미사용).
- 평문 HTTP(PORT+1) 포트는 브라우저에서도 인증서 경고 없이 열리므로, 새 기기 페어링뿐 아니라
  [초대 링크](#초대-링크-설치가입)의 안내 페이지·설치 파일 다운로드도 여기서 함께 서빙합니다.
- 첨부파일은 고정 공개 URL이 아니라 짧게 만료되는 서명 링크(`/files/<token>`)로만 내려갑니다.
- FCM은 Android 클라이언트 → Firebase → 서버(발송) → 다시 FCM → Android 기기 순으로만 쓰이고,
  Windows 클라이언트는 관여하지 않습니다.

## 기술 스택

**서버** (`server/package.json`)

| 분류 | 사용 라이브러리 |
|---|---|
| 런타임 | Node.js (ESM, `"type": "module"`) |
| 웹 프레임워크 | express ^4 |
| 실시간 | socket.io ^4 |
| DB | PostgreSQL + drizzle-orm ^0.45 / drizzle-kit ^0.31 (스키마·마이그레이션) / pg ^8 |
| 인증 | jsonwebtoken, bcryptjs |
| 파일 업로드 | multer |
| 푸시 | firebase-admin ^14 (FCM 발송) |
| TLS | selfsigned(자체 서명 인증서 생성) + Node 내장 `https` |
| 기타 | dotenv, cors |
| 운영 | pm2(선택, 개발 PC/수동 운영) 또는 nssm(설치 프로그램이 등록하는 Windows 서비스) |
| 설치 프로그램 | Inno Setup(`server/installer/messenger-server.iss`), PostgreSQL 공식 설치 프로그램(무인 모드로 같이 실행) |

**클라이언트** (`client/pubspec.yaml`)

| 분류 | 사용 라이브러리 |
|---|---|
| 프레임워크 | Flutter (Dart SDK `^3.12.2`, Windows + Android 타깃) |
| 실시간 통신 | socket_io_client, web_socket(웹소켓 커넥터 커스터마이징용) |
| HTTP | http |
| 로컬 저장 | shared_preferences(+ android 전용 백엔드), flutter_secure_storage(E2EE 키) |
| 미디어 | image_picker, file_picker, photo_view, cached_network_image, image(썸네일 가공) |
| 암호화 | cryptography(X25519/Ed25519/AES-GCM, 비밀 대화용) |
| 알림 | firebase_core, firebase_messaging(Android 전용), flutter_local_notifications |
| 데스크톱 통합 | win32, ffi, pasteboard(클립보드 이미지 붙여넣기) |

### 설치 시 자주 막히는 부분

**PostgreSQL 설치 마지막의 Stack Builder** — 아무것도 선택하지 않고 닫아도 됩니다. 서버가 쓰는
`pg`(node-postgres)는 순수 JS 드라이버라 ODBC/JDBC 드라이버가 필요 없고, PostGIS 등 확장 기능도
이 프로젝트에서 안 씁니다.

**Flutter SDK** — VS Code에 Flutter 확장을 설치하면 SDK가 없을 때 자동 다운로드 버튼이 뜹니다.
그걸로 받아도 되고 https://flutter.dev/to/setup 에서 직접 받아 압축 풀어도 됩니다. 어느 쪽이든:

- 설치 위치는 한글/공백 없는 짧은 경로로(`C:\src\flutter`, `C:\flutter` 등). `Program Files`나
  OneDrive 동기화 폴더는 피하세요.
- 설치 후 `flutter`, `flutter doctor` 명령이 안 먹으면 PATH에 자동으로 안 잡혔을 가능성이 큽니다 —
  `<SDK 경로>\bin`(예: `C:\flutter\bin`)을 사용자 환경 변수 PATH에 직접 추가하고, **열려 있던
  터미널/VS Code를 전부 닫았다가 다시 열어야** 반영됩니다.

**Visual Studio "MSVC 재배포 가능 패키지"** — 최신 Visual Studio Installer에서는 워크로드 체크
화면에 안 보일 수 있습니다. "개별 구성 요소" 탭에서 "redist"로 검색해보고, 그래도 안 보이면 최근
버전은 이 구성 요소가 워크로드에 기본 포함되어 따로 안 뜨는 경우가 많으니 기본값 그대로 설치를
진행하면 됩니다. 나중에 `flutter build windows --release` 결과물 폴더(`client/build/windows/x64/runner/Release/`)에
`msvcp140.dll` 등이 같이 생기는지로 확인할 수 있습니다.

**Android Studio는 선택 사항입니다** — 이 PC에서 Android 빌드/실행을 안 할 거면 설치 안 해도
Windows 데스크톱 개발에는 지장 없습니다. `flutter doctor`가 Android toolchain을 ✗로 표시해도
무시해도 됩니다.

**Windows 개발자 모드를 늦게 켠 경우** — `flutter run -d windows`가
`Building with plugins requires symlink support. Please enable Developer Mode...` 에러로 멈출 수
있습니다. `start ms-settings:developers`로 설정을 열어 **"개발자 모드"** 토글을 켜세요(관리자 권한
확인 + 관련 구성 요소 설치로 몇 분 걸릴 수 있음). 켠 뒤 새 터미널에서 다시 실행하면 됩니다.

**`LINK : fatal error LNK1168: ...client.exe을(를) 쓰기용으로 열 수 없습니다`** — 이전에
`flutter run -d windows`로 띄워둔 앱이 아직 실행 중이면, 빌드가 그 `client.exe`를 새로 못 써서
이 에러로 실패합니다. 떠 있는 앱 창을 닫거나(또는 작업 관리자에서 `client.exe` 프로세스를 종료)
다시 빌드하면 됩니다. 터미널을 그냥 닫아버렸을 때(창은 닫혔는데 프로세스만 남는 경우)도 흔히
겪습니다.

**다른 PC에서 `git pull`로 받은 뒤 DB 관련 기능이 그대로인 경우** — `git pull`은
`server/drizzle/*.sql` 마이그레이션 파일만 받아올 뿐, 이 PC의 DB에 자동으로 적용하지는
않습니다. pull 받을 때마다 다음을 직접 실행해야 합니다.

```powershell
cd server
npm run db:migrate
```

서버가 이미 떠 있었다면 pull 전 코드로 계속 실행 중인 상태이므로, 마이그레이션 적용 후 서버도
재시작해야( `Ctrl+C` 후 `npm start`/`npm run dev`, 또는 pm2면 `npm run pm2:restart`) 새 코드가
반영됩니다.

**Android SDK를 나중에 추가로 설치하는 경우** — Android Studio 설치 프로그램(winget
`Google.AndroidStudio` 등)으로 처음 설치한 뒤 Setup Wizard를 "Standard"로 진행해도, 아래 두 가지가
빠져서 `flutter doctor --android-licenses`가 `Android sdkmanager not found`로 실패하는 경우가
있습니다.

1. **`cmdline-tools`가 기본 설치에 안 포함됨** — Android Studio → "More Actions"(또는 Tools 메뉴)
   → **"SDK Manager"** → **"SDK Tools"** 탭 → **"Android SDK Command-line Tools (latest)"** 체크 →
   Apply
2. **`ANDROID_HOME` 환경 변수가 자동으로 안 잡힘** — 사용자 환경 변수에 직접 추가:
   ```
   ANDROID_HOME = %LOCALAPPDATA%\Android\Sdk
   ```
   PATH에도 `%ANDROID_HOME%\platform-tools`, `%ANDROID_HOME%\cmdline-tools\latest\bin` 추가 후
   터미널 재시작.

그 다음 `flutter doctor -v`가 `Flutter requires Android SDK XX and the Android BuildTools Y.Y.Y`처럼
특정 버전을 요구하면, 같은 SDK Manager에서 **"Show Package Details"**를 체크하고 **SDK Platforms**
탭에서 요구 API 레벨을, **SDK Tools** 탭의 "Android SDK Build-Tools"에서 요구 버전을 각각 체크 →
Apply로 설치합니다.

**명령줄(`sdkmanager`/`android sdk install`)로 build-tools 설치는 피하세요** — 이 프로젝트 세팅
시점의 cmdline-tools 버전에서는 `android sdk install "build-tools;28.0.3"`처럼 세미콜론이 들어간
패키지 ID로 build-tools를 설치하려 하면 도구 자체가 크래시(종료 코드 `0xC0000409`)났습니다(`platforms;android-36` 같은 플랫폼 설치는 명령줄로 문제없이 됐습니다). build-tools는 위 Android
Studio GUI의 SDK Manager로 설치하는 게 안전합니다.

```powershell
git clone <이 저장소 주소>
cd messenger_project
```

### 화상회의(LiveKit) 개발용 실행

운영 서버는 설치 프로그램이 LiveKit을 서비스로 설치해주지만([화상회의(LiveKit)](#화상회의livekit)
참고), 개발 PC에서는 직접 받아서 띄워야 합니다. 설치 프로그램(`build_server_installer.ps1`의
`$LiveKitVersion`)과 같은 버전·같은 설정으로 맞춥니다. `server/.livekit/`과 `server/.livekit-secret`은
`.gitignore` 대상이라 커밋되지 않습니다.

```bash
cd server
# 1) LiveKit 서버 실행 파일(버전은 build_server_installer.ps1의 $LiveKitVersion과 맞춘다)
mkdir -p .livekit
curl -L -o .livekit/livekit.zip https://github.com/livekit/livekit/releases/download/v1.13.7/livekit_1.13.7_windows_amd64.zip
powershell -Command "Expand-Archive .livekit/livekit.zip .livekit -Force"; rm .livekit/livekit.zip

# 2) API 비밀값 — 줄바꿈 없이 저장(서버와 livekit.yaml이 한 글자라도 다르면 인증이 깨진다)
node -e "process.stdout.write(require('crypto').randomBytes(32).toString('hex'))" > .livekit-secret

# 3) livekit.yaml — Setup-TangoTalkServer.ps1이 만드는 것과 같은 내용
printf '%s\n' "port: 7880" "rtc:" "  port_range_start: 50000" "  port_range_end: 60000" \
  "  tcp_port: 7881" "  use_external_ip: false" "turn:" "  enabled: true" "  udp_port: 3478" \
  "keys:" "  tangotalk: $(cat .livekit-secret)" > .livekit/livekit.yaml

# 4) 실행 (개발할 때마다 Node 서버와 함께 띄워둔다)
.livekit/livekit-server.exe --config .livekit/livekit.yaml
```

- **Node 서버는 LiveKit 비밀값을 시작할 때 한 번만 읽습니다** — 비밀값을 만든 뒤에는 Node 서버를
  재시작해야 화상회의가 켜지고, 클라이언트 앱도 다시 실행해야 화상회의 버튼이 나타납니다.
- 같은 PC 안에서만 테스트하면 방화벽 설정이 필요 없습니다. 다른 기기(휴대폰 등)에서 붙으려면
  TCP 7880·7881, UDP 50000-60000·3478 포트를 방화벽에서 열어야 합니다(처음 실행할 때 Windows가
  "네트워크 접근 허용" 창을 띄우면 허용).

| 변수 | 필수 | 설명 |
|---|---|---|
| `DATABASE_URL` | ✅ | PostgreSQL 접속 문자열. 자동 생성 안 됨 — 반드시 직접 채워야 합니다. 예: `postgres://messenger_app:비밀번호@localhost:5432/messenger` |
| `JWT_SECRET` | 선택 | AccessToken/RefreshToken 서명키. 비워두면 서버가 최초 실행 시 안전한 무작위 값을 만들어 `server/.jwt-secret` 파일에 저장하고 계속 재사용합니다. |
| `DB_ENCRYPTION_KEY` | 선택 | 이메일 등 민감 필드 암호화 키(32바이트/64자리 hex 고정). 비워두면 `server/.db-encryption-key`에 자동 생성/재사용. 직접 만들려면: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `PORT` | 선택 | 서버 HTTPS 포트. 기본 `3000`. |
| `PAIRING_PORT` | 선택 | 새 기기 페어링용 평문 HTTP 부트스트랩 포트. 기본 `PORT+1`. |
| `UPLOADS_DIR` | 선택 | 첨부파일 저장 위치. 기본은 `server/uploads/`. UNC 경로나 매핑된 네트워크 드라이브도 가능(예: `\\192.168.0.10\share\messenger_uploads`, `Z:\messenger_uploads`) — 항상 접근 가능해야 업로드/다운로드가 됩니다. |

**여러 서버 인스턴스를 두거나 DB를 옮길 계획이 있다면** `JWT_SECRET`/`DB_ENCRYPTION_KEY`를 반드시
`.env`에 직접 고정하세요. 자동 생성 값에 의존하면 서버 재설치 시 값이 달라져 기존 로그인 세션과
DB에 암호화 저장된 이메일을 읽을 수 없게 됩니다.

**서버 IP/도메인은 환경 변수가 아니라 클라이언트 쪽에서 관리합니다** — 서버는 자기 자신의 LAN IP를
자동으로 찾아 콘솔에 출력할 뿐, 특정 도메인/`API_BASE_URL`을 설정 파일에 못박아두지 않습니다.
클라이언트가 로그인 화면의 "서버 주소 변경"에서 주소(IP 또는 도메인 모두 가능)를 직접 입력해
`shared_preferences`에 저장하고, 이후 모든 요청이 그 주소를 씁니다. 공유기에 포트포워딩 + 고정
도메인(DDNS 등)을 연결해두면 클라이언트에는 IP 대신 그 도메인을 입력하면 됩니다.

## PostgreSQL 설정 및 마이그레이션

PostgreSQL이 설치되어 있어야 하고, 이 앱 전용 데이터베이스/계정을 하나 만들어둬야 합니다(슈퍼유저로
한 번만):

```powershell
psql -U postgres -c "CREATE USER messenger_app WITH PASSWORD '원하는_비밀번호';"
psql -U postgres -c "CREATE DATABASE messenger OWNER messenger_app;"
```

그 다음 `server/.env`의 `DATABASE_URL`을 위 계정으로 채우고(환경 변수 설정 참고), 마이그레이션을
적용합니다:

```powershell
cd server
npm install
npm run db:generate   # schema.js 기준으로 마이그레이션 SQL 생성 — 스키마(server/src/db/schema.js)를 고칠 때마다
npm run db:migrate    # 실제 DB에 적용 — 처음 실행 전 필수
```

- 스키마의 원본(source of truth)은 `server/src/db/schema.js`이고, `server/drizzle/*.sql`은
  `db:generate`가 그 변경 이력으로부터 자동 생성한 파일입니다. **SQL을 손으로 직접 고치지 않습니다.**
- 테이블 구조는 [DB 구조](#db-구조) 참고.

## 서버 실행 방법

```powershell
cd server
npm start          # 운영/일반 실행
npm run dev         # 개발용 — 파일 변경 시 자동 재시작(node --watch)
```

실행하면 콘솔에 접속 주소가 찍힙니다. 이 주소를 클라이언트 앱의 "서버 연결" 화면에 그대로
입력하세요.

```
메신저 서버 실행 중 (HTTPS, 포트 3000)
같은 와이파이의 다른 기기에서 접속할 주소:
  https://192.168.0.10:3000
```

- PC 방화벽이 처음 실행 시 "네트워크 접근 허용" 팝업을 띄우면 허용해야 다른 기기에서 접속됩니다.
- 클라이언트와 서버가 **같은 LAN(와이파이/유선망)**에 있어야 합니다. 외부망(LTE 등)에서 쓰려면
  공유기 포트포워딩 + 고정 IP(또는 DDNS)가 추가로 필요합니다.
- 첨부파일 저장 위치/용량 제한은 [환경 변수 설정](#환경-변수-설정)과 아래 [보안 및 암호화](#보안-및-암호화)를 참고하세요. 파일 업로드 용량 제한은 **1GB**입니다(`server/src/upload.js`의 `limits.fileSize`).
- 새 기기를 페어링하려면(인증서 발급) 서버 콘솔에 `pair`를 입력하고 Enter — 4자리 코드(5분간
  유효, 1회용)가 나오면 클라이언트의 "서버 주소 변경" 화면에 같이 입력합니다.

### pm2로 서버 운영하기

`node src/index.js`를 터미널에 직접 띄워두는 대신 [pm2](https://pm2.keymetrics.io/)로 관리하면
크래시 시 자동 재시작되고, 업데이트 시 재시작 명령 한 줄로 끝납니다.

```powershell
npm install -g pm2        # 최초 1회
npm run pm2:start         # 서버 시작 (= pm2 start ecosystem.config.cjs)
npm run pm2:logs          # 로그 보기
npm run pm2:restart       # 재시작 (업데이트 후)
npm run pm2:stop          # 정지
```

Windows 재부팅 시 자동으로 다시 시작되게 하려면(pm2 공식 `pm2 startup`은 Linux 전용):

```powershell
npm install -g pm2-windows-startup
pm2-startup install
pm2 save                  # 지금 떠있는 프로세스 목록을 저장 — 재부팅 후 이걸 복원함
```

**주의**: pm2로 띄우면 콘솔 입력을 받을 수 없어 `pair` 입력 방식이 안 됩니다. 대신 서버가 떠있는
같은 PC에서 다음을 실행하세요:

```powershell
npm run pair
```

(`scripts/pair.mjs`가 `pairing.js`의 `/admin/generate`를 호출 — 이 PC 안에서 온 요청만 허용되어
외부에는 열려있지 않습니다.)

### 운영 중인 서버 업데이트(DB 데이터는 그대로 두고 코드만, git 불필요)

클라이언트를 `publish_release.ps1`로 설치 파일 하나 만들어 배포하는 것과 같은 방식 —
운영 서버 PC에 git을 설치·연결할 필요 없이, 코드를 zip 파일 하나로 만들어 옮긴 뒤 그 자리에서
적용합니다.

**1) 개발 PC에서 업데이트 패키지 만들기**

```powershell
.\package_server_update.ps1
```

`server/deploy/output/server-update.zip` 하나가 만들어집니다(실데이터·비밀값은
`build_server_installer.ps1`의 스테이징과 같은 기준으로 전부 제외 — `.env`/`certs`/`uploads`/
`node_modules`/`firebase-service-account.json` 등은 애초에 안 들어갑니다).

**2) 이 zip 파일 하나만 운영 서버 PC로 옮기기** — USB, 사내 공유 폴더, 클라우드 드라이브 등
편한 방법 아무거나 사용하면 됩니다.

**3) 운영 서버 PC에서 적용하기**

```powershell
.\update_server.ps1                                    # 같은 폴더의 server-update.zip을 씀
.\update_server.ps1 -ZipPath "C:\받은위치\server-update.zip"   # 다른 경로일 때
```

순서대로 zip 풀어서 코드 적용 → `npm install`(패키지) → `npm run db:migrate`(스키마) →
`npm run pm2:restart`(재시작)를 하고, 어느 단계든 실패하면 그 자리에서 멈춥니다. **DB
데이터는 이 과정에서 전혀 건드리지 않습니다** — zip 안에 이 서버 고유의 실데이터·비밀값이
애초에 없고, `db:migrate`는 아직 적용 안 된 마이그레이션만 골라 실행하며(지금까지 모든
마이그레이션이 `CREATE TABLE`/`ALTER TABLE ADD COLUMN`류의 "추가"만 해왔습니다), pm2 재시작은
Node.js 프로세스만 내렸다 올리는 것이라 Postgres 자체에는 손대지 않습니다. 적용이 끝나면 어느
커밋에서 만든 패키지인지(`update-info.json`)도 같이 출력해줍니다.

처음 서버를 띄우는 경우(pm2에 `messenger-server`가 아직 없는 경우)는 이 스크립트 대신 위
`npm run pm2:start`를 한 번 먼저 실행하세요.

## API 목록

모든 `/api/*`, `/auth/refresh` 이후 요청은 `Authorization: Bearer <AccessToken>` 헤더가
필요합니다(`server/src/auth.js`의 `requireAuth`). `/auth/*`(회원가입/로그인/찾기류), `/health`,
`/version`, `/downloads/*`, `/files/:token`은 인증 없이 호출 가능합니다.

**인증** (`/auth`, 인증 불필요)

| Method | Path | 설명 |
|---|---|---|
| GET | `/auth/username-available` | 아이디 중복 확인 |
| POST | `/auth/register` | 회원가입(보안 질문/답변 필수) |
| POST | `/auth/find-id` | 이메일로 아이디 찾기 |
| POST | `/auth/security-question` | 아이디+이메일 일치 확인 후 보안 질문 반환 |
| POST | `/auth/verify-security-answer` | 보안 질문 답변만 검증(비밀번호는 안 바꿈) |
| POST | `/auth/reset-password` | 비밀번호 재설정(이메일+보안 질문 답변 확인) |
| POST | `/auth/login` | 로그인 |
| POST | `/auth/refresh` | AccessToken 재발급 |

**사용자/프로필** (`/api`, 인증 필요)

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/users` | 활성 가입자 전체 목록(방 생성·팀원 추가·조직도용, 계정 등급 `role` 포함). `position`은 부서·직책 관리 범위가 '계정 단위'일 때만 채워지고, '팀 단위'면 항상 `null`(팀마다 다를 수 있어 이 서버 전체 목록 하나로는 못 정한다) |

| POST | `/api/users/me/withdraw` | 회원 탈퇴 |
| GET | `/api/position-options` | 직책 목록 조회(서열순) — 위 관리자 콘솔 전용 버전과 달리 서버 운영자가 아니어도 누구나 호출 가능. "팀 초대 링크 만들기"의 "부여할 직책"이 쓴다 |

| 서버→클라이언트 | `secret:invite` / `secret:accepted` / `secret:rejected` / `secret:left` | 비밀 대화 생명주기 |

PostgreSQL, `drizzle-orm`으로 접근(원본 스키마: `server/src/db/schema.js`). 쿼리 함수는

## FCM 푸시 알림 설정

FCM은 **Android 전용**입니다(Windows는 Firebase가 공식 지원하지 않아, 코드에서
`Platform.isAndroid`로 완전히 분기 — `client/lib/main.dart`, `server/src/push.js` 참고).
Firebase 프로젝트를 아직 설정 안 했어도(또는 서비스 계정 키가 없어도) 서버/클라이언트 모두
정상 동작하며, 그 경우 푸시 발송만 조용히 비활성화됩니다.

**클라이언트 빌드에 `google-services.json`을 넣는 방식은 쓰지 않습니다.** 이 제품은 서버까지
고객사가 직접 운영하는 자체 호스팅 제품이라, 고객사마다 앱을 따로 빌드해 줘야 하는 문제를
피하려고 Firebase 설정 전체(클라이언트 초기화 값 + 서버 발송용 서비스 계정 키)를 **관리자
콘솔**에서 입력받아 DB(`server_settings` 테이블)에 저장합니다. 그래서 APK/설치 프로그램은
고객사와 무관하게 하나만 빌드하면 되고, 각 고객사가 자기 서버에서 자기 Firebase 프로젝트 값을
넣는 것으로 끝납니다. 클라이언트는 `GET /firebase-client-config`(인증 불필요 — Android 클라이언트
API 키는 패키지명+SHA-1로 제한돼 비밀값이 아닙니다)로 이 값을 받아 로컬에 캐싱하고, 코드로
직접 `Firebase.initializeApp(options: FirebaseOptions(...))`을 호출합니다
(`client/lib/services/fcm_config_cache.dart`, `main.dart`, `session.dart` 참고).

**설정 절차 (관리자 콘솔 → 서버 관리 → 운영 현황 → FCM 설정)**

1. [Firebase 콘솔](https://console.firebase.google.com/)에서 프로젝트 생성
2. Android 앱 추가 — 패키지 이름에 정확히 `com.teamtalk.messenger` 입력(다르면 알림이 안 옵니다)
3. 등록 후 나오는 4개 값을 관리자 콘솔에 그대로 입력 — Firebase 콘솔 화면에 바로 안 보이면
   대신 다운로드한 `google-services.json`을 열어서 아래처럼 옮기면 됩니다(필드 이름이 관리자
   콘솔 항목명과 다르게 적혀 있어서 헷갈리기 쉽습니다):

   | 관리자 콘솔 항목 | `google-services.json` 안의 위치 |
   |---|---|
   | API 키 | `client[0].api_key[0].current_key` |
   | 앱 ID | `client[0].client_info.mobilesdk_app_id` |
   | 프로젝트 ID | `project_info.project_id` |
   | 발신자 ID | `project_info.project_number` |

4. Firebase 콘솔 → 프로젝트 설정 → 서비스 계정 → "새 비공개 키 생성" → 받은 JSON 파일 내용을
   그대로 복사해서 관리자 콘솔의 서비스 계정 입력창에 붙여넣고 저장
5. 저장 즉시 반영됩니다(서버 재시작 불필요 — `push.js`가 캐시를 지우고 다음 발송부터 새 설정을
   씁니다). 클라이언트도 다음 로그인 시 새 값을 받아 초기화합니다.

서버가 서비스 계정을 응답으로 다시 보여주는 일은 없습니다(`private_key` 노출 방지) — 설정
여부와 어느 계정인지(`client_email`)만 보여줍니다. 이미 예전 방식(`server/firebase-service-account.json`
파일)으로 설정해둔 서버는 그대로 동작합니다 — DB 값이 비어 있을 때만 이 파일을 폴백으로 봅니다.
다만 파일을 나중에 새로 갖다놓거나 교체하는 경우, 그 전에 한 번이라도 발송을 시도해서 "설정
없음" 상태가 이미 캐시됐다면 서버를 재시작해야 반영됩니다 — 관리자 콘솔에 JSON을 붙여넣어
저장하면 이 문제 없이 즉시 반영되므로, 파일 방식보다 관리자 콘솔 쪽을 더 권장합니다.

**설계 메모**: 알림은 `notification` 페이로드가 아니라 `data`(data-only)로만 보냅니다 — 그래야
앱이 완전히 꺼져 있을 때도 OS가 자체 렌더링하지 않고 `onBackgroundMessage` 핸들러가 호출되어,
실시간 소켓으로 받는 알림과 똑같은 모양(발신자 아바타, 자물쇠 배지 등)으로 그릴 수 있습니다. 이미
소켓이 연결된(=앱이 떠있는) 기기에는 중복 발송하지 않습니다.

## 화상회의(LiveKit)

1:1과 그룹 회의를 같은 방식으로 처리합니다 — LiveKit(SFU)이 미디어를 중계하고, 1:1도 "참가자가
두 명인 방"일 뿐입니다. P2P 경로를 따로 두지 않아 유지할 코드가 하나뿐이고, 사내망에서는
NAT 문제도 생기지 않습니다. 미디어는 **클라이언트와 LiveKit이 직접** 주고받고 Node 서버는 그
경로에 끼지 않습니다 — Node 서버는 "이 사람이 이 방에 들어가도 된다"는 참가 토큰만 발급합니다
(`server/src/calls.js`).

**설치**: 서버 설치 프로그램(`build_server_installer.ps1`로 만든 `tangotalk-server-setup.exe`)이
LiveKit 실행 파일을 같이 넣고, 설치 시점에 다음을 자동으로 처리합니다.

- API 비밀값 생성(`server/.livekit-secret`)과 그 값을 그대로 쓴 `livekit.yaml` 작성 —
  **Node 서버와 LiveKit이 같은 비밀값을 알아야** 토큰 서명/검증이 맞물립니다
- `TangoTalkLiveKit` 이름의 Windows 서비스 등록(NSSM, 자동 시작)
- 방화벽 규칙: TCP 7880·7881(신호), UDP 50000-60000(미디어), UDP 3478 + 30000-40000(내장 TURN)

방화벽 포트 중 **하나라도 막히면 "통화는 연결됐는데 화면이 안 나오는"** 상태가 됩니다. 내장
TURN을 켜두는 이유도 이것으로, UDP 직결이 막힌 사내망에서 중계로라도 붙게 하기 위함입니다.

**LiveKit이 없으면 화상회의만 꺼집니다.** 서버는 그대로 동작하고 클라이언트는 통화 버튼 자체를
감춥니다(`GET /api/calls/config`가 `enabled: false`). 그래서 기존 서버를 코드만 업데이트한
경우(`Update-Server.ps1`)에는 화상회의가 꺼진 상태로 남습니다 — 쓰려면 설치 프로그램으로 다시
설치해야 LiveKit이 들어갑니다.

**비밀 대화(E2EE)에서는 화상회의를 막아뒀습니다** — SFU는 미디어를 복호화해서 중계하는
구성요소라 "서버가 내용을 알 수 없다"는 약속과 충돌하기 때문입니다(대화 내보내기를 막아둔 것과
같은 이유). LiveKit 자체는 E2EE를 지원하므로 나중에 열 수 있습니다.

**녹화는 넣지 않았습니다.** LiveKit의 녹화 컴포넌트(Egress)는 바이너리 배포가 없고 Docker 전용
(+Redis)이라 Windows 설치 모델과 맞지 않고, 클라이언트 녹화도 Windows에 쓸 만한 부품이
없습니다(`flutter_webrtc`의 MediaRecorder는 Windows 미구현). 대신 통화가 끝나면 그 대화에
`화상회의 · 12분 · 홍길동, 김철수 참여`(아무도 안 받으면 `부재중 화상회의`) 한 줄이 남습니다.

## Android 릴리즈 서명

release 빌드에는 서명이 필요합니다 — 서명 없이는 배포는커녕 기존 설치본 위에 업데이트 설치도
안 됩니다. 최초 1회만 만들면 계속 재사용합니다(**꼭 안전하게 보관** — 잃어버리면 이후 업데이트를
기존 설치본에 덮어씌울 수 없고 사용자들이 재설치해야 합니다):

```powershell
& "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe" -genkey -v -keystore client\android\upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

(Android Studio 설치 경로는 설치 방식에 따라 `C:\Program Files\Android Studio\` 인 경우도 있습니다 —
`keytool.exe`가 안 보이면 `Get-ChildItem "C:\Program Files" -Recurse -Filter keytool.exe`로 찾으세요.)

그다음 `client/android/key.properties`를 만듭니다(`.gitignore`에 있어 git엔 안 올라감):

```
storePassword=<keystore 비밀번호>
keyPassword=<키 비밀번호>
keyAlias=upload
storeFile=../upload-keystore.jks
```

이 파일이 없으면 release 빌드는 디버그 키로 자동 폴백합니다. `client/android/app/build.gradle.kts`는
debug 빌드도 release와 같은 키로 서명하도록 되어 있습니다 — 실기기에 이미 release 서명으로 설치된
앱 위에 debug 빌드를 덮어씌울 때 "signatures do not match"로 설치가 거부되는 걸 막기 위함입니다
(`key.properties`가 없으면 표준 디버그 키로 자동 폴백해서 빌드는 그냥 됩니다).

### SHA-1/SHA-256 지문 확인

Firebase 콘솔 등록이나 Google Cloud Console의 API 키 제한(패키지명+서명 지문)에 필요합니다.
가장 정확한 방법은 Gradle이 실제 빌드에 쓰는 서명 설정을 그대로 보여주는 `signingReport`입니다
(`key.properties` 유무에 따라 어떤 키가 어떤 variant에 쓰이는지까지 한 번에 나옵니다):

```powershell
$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"   # PowerShell엔 JAVA_HOME이 기본으로 없어서 gradlew가 "JAVA_HOME is not set" 오류로 실패한다 — 이 창에서만 적용, 영구 적용하려면 setx 사용
cd client\android
.\gradlew signingReport
```

`:app:signingReport` 항목에서 `Variant: release`(배포용 apk가 실제로 서명되는 키)의 SHA1 값을
씁니다. `key.properties`가 있는 이 프로젝트는 `debug` variant도 같은(release) 키로 서명되므로,
로컬에서 `flutter run`으로 테스트할 때도 이 SHA1이 적용됩니다 — 등록은 이거 하나로 충분합니다.
(keytool로 직접 확인하는 방법도 있지만 `-list -v`가 일부 Windows/한국어 로케일 JDK 조합에서
포맷 오류로 깨지는 경우가 있어, gradlew 방식을 권장합니다.)

## 서버 배포 및 업데이트

### 클라이언트 버전 배포

클라이언트는 앱을 시작할 때마다 서버의 `/version`을 확인해서, 서버에 더 최신 버전이 올라와 있으면
화면에 배너로 알려줍니다. 새 버전을 배포하려면 `client/pubspec.yaml`의 `version:`을 올린 뒤,
저장소 루트에서 한 번에:

```powershell
.\publish_release.ps1 -Version "1.0.7" -Notes "이번 업데이트 내용"
```

Android/Windows 릴리즈 빌드, 설치 프로그램 컴파일, `server/releases/`로 복사, `version.json` 작성까지
전부 자동으로 처리합니다. 서버는 재시작 없이 바로 새 버전을 알려주기 시작합니다.

켜져 있는 앱에 알약이 뜨는 경로는 세 가지이고, 어느 하나가 빠져도 나머지가 메웁니다:
`version.json`이 바뀌는 순간의 브로드캐스트(`/updates` 네임스페이스), 그 소켓에 **붙을 때마다**
서버가 알려주는 현재 버전(배포 순간에 절전·네트워크 끊김이었거나 그 뒤 서버가 재시작된 경우를
복구), 그리고 앱이 켜져 있는 동안 30분마다 하는 `GET /version` 재확인(소켓이 아예 못 붙은
경우까지).

**VC++ 런타임은 앱과 같이 배포됩니다.** `msvcp140.dll`/`vcruntime140.dll` 등을 `client.exe`
옆에 넣어서(`client/windows/CMakeLists.txt`) 설치한 PC의 `C:\Windows\System32` 쪽 재배포
패키지를 아예 쓰지 않습니다. MSVC는 "대상 PC의 재배포 패키지가 빌드에 쓴 툴셋 버전 이상"이길
요구하는데, 그보다 낮으면 앱은 멀쩡히 켜지고 **실행 중에** 0xc0000005로 죽습니다(툴셋 14.40부터
`std::mutex` 생성자가 바뀐 탓이 큽니다). 개발 PC는 늘 최신 런타임이라 재현이 안 되고 남의
PC에서만 터지므로, 이벤트 뷰어에 **오류 모듈이 `MSVCP140.dll`/`VCRUNTIME140.dll`로 찍히면**
이걸 의심하세요.

**PC 앱에서 한글을 빠르게 치면 글자가 빠지던 문제.** Windows에서 Flutter는 키를 누를 때마다 먼저
Dart 쪽 답을 받은 뒤에야 그 키를 한글 입력기(IME)에 넘깁니다. 그 순간 UI 스레드가 30ms쯤만 다른
일에 붙잡혀 있어도 조합이 꼬여 "안녕하세요"가 "안하셍"처럼 됩니다(영어는 같은 상황에서도 멀쩡 —
입력칸 코드와 무관하게 재현됨). 이 앱은 세션 알림(읽음 표시·접속 상태·새 메시지 등) 하나에 방 목록과
대화 목록 전체를 다시 그리므로, **IME 조합 중에는 그 알림을 모아 두었다가** 0.4초 손을 멈추거나
메시지를 보낼 때 내보냅니다(쉬지 않고 쳐도 2초가 지나면 다음 띄어쓰기에서, 늦어도 5초에는
내보냄 — `client/lib/services/typing_gate.dart`). `Session`/`RoomChatController`의
`notifyListeners`가 이 게이트를 거치므로, 새로 무거운 화면 갱신을 붙일 때도 같은 길로 보내세요.

받는 쪽은: Windows는 `messenger-setup.exe`를 받아 실행하면 설치 마법사가 뜨고, Android는 apk를
받아서 탭하면 설치 화면으로 넘어갑니다(둘 다 "출처를 알 수 없는 앱/파일 실행" 확인이 한 번은
필요합니다 — 스토어를 거치지 않는 배포 방식의 한계).

### 개발 PC → 운영(서버) PC 코드 업데이트

이 저장소를 Git 원격(GitHub 등)에 올려두고, 서버 PC에서는 clone 후 아래를 반복합니다. **순서가
중요합니다** — 새 코드가 새 스키마를 기대하는 상태로 먼저 뜨면 오류가 납니다:

```powershell
cd server
git pull
npm install          # package.json이 바뀌었을 때만
npm run db:migrate   # server/src/db/schema.js가 바뀌었을 때만(=drizzle/에 새 마이그레이션 파일이 추가됐을 때)
npm run pm2:restart  # 또는 pm2 없이 직접 재시작
```

`.env`, `certs/`, `uploads/`, `releases/`, `firebase-service-account.json`은 모두 `.gitignore`에
있어 `git pull`이 건드리지 않습니다 — 서버를 처음 새 PC에 놓을 때는 이 파일들을 별도로(USB, 압축
파일 등으로) 옮겨야 합니다.

**개발 PC 여러 대를 오갈 때도 똑같습니다.** 집 PC에서 만든 마이그레이션을 개발 PC로 `git pull`
받은 뒤 `npm run db:migrate`를 잊으면, 서버는 멀쩡히 뜨고 로그인도 되는데 새 컬럼을 읽는 화면만
`teams.icon_url 칼럼 없음` 같은 쿼리 오류로 **비어 보입니다**(DB 데이터는 멀쩡합니다). 이제는
서버가 뜨기 전에 원장과 `drizzle/`을 대조해서 미적용 마이그레이션이 있으면 콘솔에 크게 알립니다
(`server/src/migrationCheck.js`). 더 자세히 보려면 `node scripts/check-migrations.mjs`.

### 새 서비스 PC에 네이티브 설치 프로그램으로 설치/업데이트

위의 git pull 방식과 별개로, Node.js/PostgreSQL을 하나도 안 깔아본 새 "서비스 PC"에 서버+DB를
한 번에 세팅하는 Windows 설치 프로그램이 있습니다(`server/installer/`). 설치하는 사람이 비밀번호나
DB 계정을 직접 다룰 필요가 없습니다 — 전부 설치 프로그램이 자동으로 만들고 내부적으로만 씁니다.

**설치 프로그램 만들기** (저장소 루트에서):

```powershell
.\build_server_installer.ps1
```

Node.js 포터블 런타임, PostgreSQL 공식 설치 프로그램, `nssm.exe`를 `server/installer/bin/`에
받아두고(이미 있으면 재사용), `server/`를 정리해서(`.env`/`certs`/`uploads`/로그/
`firebase-service-account.json` 등 실데이터·비밀값 제외) `npm install`까지 마친 결과를
`server/installer/stage/`에 만든 뒤, `server/installer/output/tangotalk-server-setup.exe`를
컴파일합니다. (`server/releases/`와는 무관한 별개 산출물입니다 — 클라이언트 자동 업데이트
채널이 아니라 USB/사내 공유 폴더 등으로 직접 전달하는 용도입니다.)

**새 PC에 설치**: `tangotalk-server-setup.exe`를 관리자 권한으로 실행하면 —

- PostgreSQL을 이 앱 전용 경로(`C:\TangoTalk-Server\pgsql`)와 전용 포트(`55432`)에 무인 설치합니다
  (그 PC에 이미 다른 PostgreSQL이 있어도 충돌하지 않습니다).
- `messenger_app` 역할/`messenger` 데이터베이스를 만들고 마이그레이션까지 적용합니다.
- 방화벽 규칙을 추가합니다.
- 설치 중 고르는 대로 서버를 **백그라운드 Windows 서비스**(NSSM, 부팅 시 자동 시작·창 없음,
  서비스 이름 `TangoTalkServer`) 또는 **콘솔 창**(시작 메뉴 "서버 콘솔로 실행")으로 등록합니다.
- 시작 메뉴에 "새 기기 페어링 코드 발급"(콘솔이 없는 서비스 모드에서 `pair` 입력을 대신함),
  "메신저 설명서"(예전 이름 "도움말" — **이 README.md 전체**를 목차 링크가 실제로 동작하는 정적 웹페이지로 변환해서
  기본 브라우저로 보여줌 — `build_server_installer.ps1`이 빌드 시 `build-readme-html.mjs`로
  매번 새로 만들므로 설치할 때마다 최신 버전으로 덮어써짐), "서버 업데이트", "서버 재시작",
  "첨부파일 저장소", "DB 데이터 초기화", "서버 완전 삭제(PostgreSQL·Node 앱·DB 데이터 모두)"도
  같이 설치됩니다. 뒤의 다섯은 목적이 다릅니다:
  - **서버 업데이트**(`Update-Server.ps1`) — 개발 PC에서 `package_server_update.ps1`로 만든
    업데이트 zip을 파일 선택 창에서 고르고 "업데이트 시작"을 누르면, 코드 적용 → `npm
    install` → DB 마이그레이션(추가만 함, 기존 데이터 안 건드림) → 서버 재시작까지 자동으로
    진행됩니다 — **평소 코드를 업데이트할 때** 씁니다.
  - **서버 재시작**(`Restart-Server.ps1`) — 코드/DB는 전혀 건드리지 않고 `TangoTalkServer`
    서비스만 다시 시작합니다 — `.env`를 손으로 고쳤거나, 서버가 이상하게 응답할 때 빠르게
    다시 띄우고 싶을 때 씁니다(설치 프로그램을 다시 실행할 필요 없음).
  - **첨부파일 저장소**(`Storage-Path.ps1`) — 지금 첨부파일이 저장되는 위치(기본값
    `{app}\server\uploads`)를 보여주고, NAS나 다른 PC의 공유 폴더(`\\서버\공유\폴더`)
    등으로 바꿀 수 있습니다. 기존 파일이 있으면 새 위치로 옮길지 물어보고, `.env`의
    `UPLOADS_DIR`을 갱신한 뒤 서비스를 재시작합니다 — **첨부파일을 서버 PC가 아니라 별도
    저장소에 두고 싶을 때** 씁니다.
  - **DB 데이터 초기화**(`Reset-Data.ps1`) — 서버는 그대로 두고 회원/팀/메시지/댓글/첨부파일
    등 데이터만 비웁니다. `.env`/인증서/설치는 안 건드리고, 끝나면 서버가 다시 시작되어 바로
    빈 상태로 쓸 수 있습니다(처음 가입하는 계정이 새 운영자가 됨) — **서버를 계속 쓰면서
    데이터만 새로 시작하고 싶을 때** 씁니다.
  - **서버 완전 삭제(PostgreSQL·Node 앱·DB 데이터 모두)**(`Uninstall-Full.ps1`) — DB/업로드/
    인증서/`.env`/비밀값을 지우고, **PostgreSQL 자체도 `uninstall-postgresql.exe`로 정식
    제거**합니다(서비스 등록까지 해제됨 — 프로그램 파일만 남기고 서비스만 정지시키면, 나중에
    같은 PC에 PostgreSQL을 다시 설치할 때 설치 프로그램이 "이미 설치돼 있다"고 인식해서 새로
    지정한 경로/서비스 이름을 무시하고 예전 설치를 그대로 재사용해버리는 문제가 있어서입니다).
    마지막 단계로 **일반 "TangoTalk 서버 제거"(unins000.exe)를 무인 모드로 자동 실행**해서
    Node 앱 프로그램 파일까지 마저 지웁니다 — 이 스크립트 하나로 서버 전체가 걷어내집니다.
    **서버 자체를 걷어낼 때** 씁니다.

  이 중 "DB 데이터 초기화"/"서버 완전 삭제" 둘만 일반 제거로는 지워지지 않는 실데이터를
  다루므로, **실제 서버 운영자(`is_server_admin=true`) 계정의 아이디/비밀번호로 먼저 본인
  확인**을 해야만(`scripts/verify-admin.mjs`) 각각 `RESET`/`DELETE` 입력 확인까지 진행됩니다
  — 이 PC 앞에 앉을 수 있다는 것만으로는 지울 수 없게 한 것입니다. 넷 다 NSSM 서비스를
  다루므로 관리자 권한이 필요해서, 관리자가 아니면 스스로 관리자 권한으로 다시 실행합니다.

  **주의**: Windows "설정 → 앱 → 설치된 앱"에서 TangoTalk 서버를 지우는 것은 시작 메뉴의
  **"TangoTalk 서버 제거"**와 완전히 같은 동작입니다(같은 `unins000.exe`를 실행) — **Node 앱
  프로그램 파일만** 지우고 PostgreSQL·DB 데이터·업로드 파일·인증서·`.env`·비밀값은 전혀
  건드리지 않습니다(PostgreSQL 서비스도 계속 떠 있음). "서버 완전 삭제" 바로가기는 이
  "TangoTalk 서버 제거"를 **마지막 단계로 포함**하면서 그 앞에 PostgreSQL·DB 데이터 삭제를
  더한 것입니다. 그래서 정말로 전부 지우고 싶다면 Windows "설치된 앱"이 아니라 반드시
  **"서버 완전 삭제" 바로가기**를 써야 합니다 — 그렇지 않으면 "지웠다"고 생각해도 실제
  데이터는 그대로 남아있게 됩니다.

**업데이트**: 평소에는 시작 메뉴의 "서버 업데이트"(위 설명)로 충분합니다. 완전히 새 
설치 프로그램을 다시 배포하고 싶을 때는 `build_server_installer.ps1`을 돌려서 만든 최신
`tangotalk-server-setup.exe`를 같은 PC에서 다시 실행하면 됩니다 — 이미 설치돼 있는 걸
감지해서 PostgreSQL 재설치나 DB 비밀번호 재생성 없이, 프로그램 파일만 새로 덮어쓰고 새로
추가된 마이그레이션만 적용한 뒤 서비스를
재시작합니다(기존 `.env`/DB/업로드는 그대로 보존).

자세한 설계 배경과 유지보수 메모, 검증 체크리스트는 `server/installer/README.md` 참고.

## 서버/DB 백업 · 이전 · 초기화

### 백업

**설치 프로그램으로 설치한 서버**는 시작 메뉴의 **"백업"**을 누르면 됩니다 — 경로/포트/비밀번호를
몰라도 콘솔 명령어 없이 바로 `<설치 경로>\backups\messenger_<날짜시각>.dump`로 저장됩니다
(`server/installer/Backup-Data.ps1`). 되돌릴 땐 **"복원"**을 눌러 그 파일을 고르면 됩니다 — DB
데이터 초기화와 같은 수준의 안전장치(운영자 본인 확인 + `RESTORE` 입력)가 있습니다.

아래는 저장소를 직접 clone해서 돌리는 개발 환경(시스템 PostgreSQL 사용)일 때의 수동 명령어입니다:

```powershell
"C:\Program Files\PostgreSQL\<버전>\bin\pg_dump.exe" -U messenger_app -d messenger -F c -f messenger_backup.dump
```

`server/certs/`, `server/uploads/`, `server/.env`, `server/firebase-service-account.json`,
`server/releases/`도 Git에 없는 실데이터이므로 함께 백업하세요(예: 압축해서 통째로) — 위 "백업"
바로가기는 DB만 백업합니다.

### 다른 PC로 이전

1. 새 PC에 [개발 환경 준비](#개발-환경-준비)대로 Node.js/PostgreSQL 설치, 저장소 clone
2. [PostgreSQL 설정 및 마이그레이션](#postgresql-설정-및-마이그레이션)대로 계정/DB 생성
3. 덤프 복원:
   ```powershell
   "C:\Program Files\PostgreSQL\<버전>\bin\pg_restore.exe" -U messenger_app -d messenger --clean --if-exists messenger_backup.dump
   ```
4. 백업해둔 `.env`, `certs/`, `uploads/`, `firebase-service-account.json`, `releases/`를 그대로
   복사해 넣기 — **특히 `certs/`를 그대로 옮기면 클라이언트를 재빌드하지 않아도 됩니다**(인증서가
   바뀌지 않으므로). 새로 생성하게 두면(=옮기지 않으면) 클라이언트가 페어링을 다시 받아야 합니다.
5. `npm install` → `npm run db:migrate`(복원한 덤프가 이미 최신 스키마라면 변경 없음으로 끝남) →
   서버 시작

### DB 데이터 전부 삭제(테이블 구조는 유지)

```powershell
psql -U messenger_app -d messenger -c "TRUNCATE TABLE secret_rekeys, secret_sessions, message_comments, messages, room_members, devices, rooms, users RESTART IDENTITY CASCADE;"
```

첨부파일 실물(`server/uploads/`)은 이 명령으로 지워지지 않습니다 — 필요하면 폴더도 따로 비우세요.

## 보안 및 암호화

- **전송 구간**: 서버가 스스로 만든 자체 서명 TLS 인증서(RSA 2048, 유효기간 10년)를 쓰고,
  클라이언트는 공인 CA 목록이 아니라 **그 인증서 하나만** 신뢰하도록 고정(핀닝)합니다
  (`client/lib/services/pinned_tls.dart`). 인증서는 앱 빌드에 내장되거나(`assets/server_cert.pem`),
  페어링 코드로 나중에 동적으로 받아 로컬에 저장됩니다.
- **비밀번호**: bcrypt로 해시 저장(원문 저장 안 함).
- **인증 토큰**: JWT AccessToken(1시간)/RefreshToken(30일). 비밀번호 변경/탈퇴/로그아웃 시
  `tokenVersion`을 올려 기존에 발급된 모든 토큰을 무효화합니다.
- **DB 저장 민감 필드**: 이메일은 AES-256-GCM으로 암호화 저장(`emailEnc`)하고, "정확히 일치하는지"
  조회할 때는 별도의 HMAC-SHA256 해시(`emailLookup`)를 씁니다 — 이 해시만으로는 원문을 복원할 수
  없습니다(`server/src/crypto.js`).
- **보안 질문 답변**: 이메일과 별개로 bcrypt 해시 저장.
- **첨부파일 다운로드**: 고정 공개 경로가 없고, 요청마다 짧게 만료(최대 2시간)되는 서명 링크
  (`/files/<token>`)만 발급됩니다(`server/src/upload.js`).
- **비밀 대화(E2EE)**: 기기별 X25519(키 교환)/Ed25519(서명) 키쌍을 클라이언트에서 생성하고 개인키는
  `flutter_secure_storage`에만 저장 — 서버에는 절대 오지 않습니다. 임시 공개키는 기기 장기 신원키로
  서명해서 서버가 키를 바꿔치기하는 중간자 공격을 막습니다. 서버 DB(`secret_sessions`/`secret_rekeys`)에는
  공개키·서명·상태값만 저장되고, 실제 대화 내용/공유비밀/체인키는 전혀 저장되지 않습니다.
- **비밀 대화 자동 삭제**: 만료된 메시지는 DB 행뿐 아니라 첨부파일 실물까지 완전히 삭제합니다
  (`server/src/secretExpiry.js`, 5초 간격 스윕).
- **탈퇴 계정 보존기간**: 탈퇴 후 1년이 지나면 그 계정이 보낸 메시지를 자동 파기합니다(첨부파일은
  유지 — `server/src/retention.js`).

## Git 관리 규칙

`.gitignore`(루트/`server/`/`client/`/`client/android/`)에 의해 아래 항목은 커밋되지 않습니다 —
**절대 GitHub 등 원격에 올리면 안 되는 파일들**입니다:

- `server/.env`, `server/.jwt-secret`, `server/.db-encryption-key`
- `server/certs/`(TLS 개인키 포함)
- `server/firebase-service-account.json`(FCM 발송용 Firebase 관리자 키 — 예전 방식의 폴백 파일.
  새 설치는 관리자 콘솔에서 입력해 DB에 저장하므로 이 파일 자체가 없어도 됩니다)
- `server/uploads/`, `server/releases/`, `server/db.json`
- `client/android/key.properties`, `client/android/**/*.jks`, `client/android/**/*.keystore`
- 그 외 각 플랫폼의 표준 빌드 산출물(`build/`, `.dart_tool/` 등)

`client/android/app/google-services.json`은 더 이상 빌드에서 쓰지 않습니다(FCM 설정 참고) —
있어도 무시되니 지워도 되고, 실수로 커밋해도 예전만큼 걱정할 값은 아닙니다.

## 문제 해결

| 증상 | 원인 / 조치 |
|---|---|
| 클라이언트에서 서버 연결이 안 됨(TLS 오류) | 서버 PC의 LAN IP가 바뀌었거나 인증서가 재생성됨 → 서버 콘솔에 `pair` 입력 후 클라이언트에서 새 코드로 다시 페어링 |
| `flutter build windows`가 심볼릭 링크 오류로 실패 | Windows 개발자 모드가 꺼져 있음 → `start ms-settings:developers`로 켜기 |
| Android 기기에 apk 설치 시 "signatures do not match" | 기존 설치본과 서명이 다름(예: keystore 없이 디버그로 빌드) → [Android 릴리즈 서명](#android-릴리즈-서명)대로 `key.properties` 설정 후 재빌드, 또는 기존 앱 삭제 후 재설치 |
| FCM 알림이 전혀 안 옴 | ① 관리자 콘솔 → 서버 관리 → 운영 현황 → FCM 설정에서 4개 값과 서비스 계정이 다 채워져 있는지 확인 ② 클라이언트가 로그인 이후에야 이 값을 받아 초기화하므로, 설정 직후라면 한 번 재로그인해서 확인 ③ Windows 클라이언트는 애초에 FCM 미지원(정상) |
| 팀 목록이 비어 보이고 `... 칼럼 없음` 오류 | 다른 PC에서 만든 마이그레이션을 `git pull`로 받고 `npm run db:migrate`를 안 한 것. 서버 시작 로그에 미적용 목록이 찍힌다. 데이터는 멀쩡하니 `npm run db:migrate`만 하면 된다. 그래도 `db:migrate`가 조용히 아무것도 안 하면, **이미 적용된 마이그레이션의 해시가 원장에 없어서** 거기서 막힌 것이다(그 뒤 마이그레이션이 전부 안 돌아간다) — `node scripts/check-migrations.mjs`로 어느 것인지 확인한다 |
| `npm run db:migrate` 실패 | `DATABASE_URL`이 올바른지, PostgreSQL 서비스가 떠있는지 확인. 스키마 충돌이면 `server/drizzle/meta/`의 마이그레이션 이력과 실제 DB 상태가 어긋난 것 — 백업 후 [DB 데이터 전부 삭제](#db-데이터-전부-삭제테이블-구조는-유지) 후 재적용을 고려 |
| `npm run db:migrate`는 "성공"이라고 뜨는데 새 테이블/컬럼이 실제로는 안 보임 | `drizzle.__drizzle_migrations`에 기록된 시각(`created_at`)이 실제보다 미래로 잘못 들어가 있으면, 그보다 실제 시각이 이른 새 마이그레이션들이 "이미 적용됨"으로 착각되어 조용히 건너뛰어질 수 있다(과거 개발 DB에서 실제로 있었던 문제). `server` 폴더에서 `node scripts/check-migrations.mjs`(읽기 전용, DB를 고치지 않음)를 실행하면 어떤 마이그레이션이 빠졌는지와 실제 테이블 상태를 확인할 수 있다 |
| pm2로 띄운 뒤 페어링 코드를 못 받음 | pm2는 콘솔 입력을 못 받음 → 서버가 떠있는 같은 PC에서 `npm run pair` 실행 |
| 첨부파일이 업로드/다운로드 안 됨(네트워크 드라이브 사용 시) | `UPLOADS_DIR`로 지정한 UNC 경로/네트워크 드라이브가 서버 PC에서 항상 접근 가능한지 확인 |
| 특정 화면만 "요청이 시간 초과되었습니다"로 계속 실패 | 그 API가 서버에서 에러를 던졌는데(예: DB 마이그레이션이 아직 안 된 테이블/컬럼 조회) `express-async-errors`+공통 에러 미들웨어(`server/src/index.js`) 덕에 이제는 빠르게 실제 에러 메시지로 응답한다 — 예전처럼 응답 없이 멈추지 않는다. 그래도 시간 초과가 뜬다면 그 API 자체에 도달을 못 하는 것이므로(서버가 안 떠 있거나 네트워크 문제) `npm run db:migrate`를 그 서버에서 실행했는지부터 확인 |
